# Pitfalls: anti-pattern ที่เกิดซ้ำ เรียงตามผลกระทบ

> หลักฐานมาจากประวัติแชทของตัวเอง (ส.ค.-ก.ย. 2026) อ้างเป็นโปรเจกต์ + วันที่ (เดือน-วัน) เท่านั้น ไม่มีค่า secret ไม่มีชื่อบุคคล ไม่มีตัวระบุโรงพยาบาล ไม่มีข้อมูลสุขภาพ
>
> คอลัมน์ "วิธีแก้ในคลัง" ชี้ไปยังไฟล์ กติกา prompt หรือสกิลที่มีอยู่จริงในคลัง `D:\ai-playbook`

ลำดับโดยรวม: 1 ขยายขอบเขต, 2 ความต้องการแกว่ง, 3 ตัวส่งสารระหว่าง agent, 4 ข้อมูลหายหลัง /clear, 5 ความลับในแชท, 6 อนุมัติหมด, 7 process/CI เกินตัว, 8 ตรวจความเป็นไปได้ช้า, 9 หลาย agent ชน repo เดียว, 10 โควตาหมด, 11 stack/ชื่อเปลี่ยนไปมา, 12 ตอบ setup ซ้ำ, 13 รั้วที่ต้องพิมพ์ซ้ำ, 14 Windows long path

## 1. ขยายขอบเขตด้วยคำว่า "world-class"

- **อาการ**: พิมพ์ "ทำให้ดีที่สุด / ระดับโลก / ละเอียดที่สุด / ดูทั้งระบบทุกด้าน" แล้ว agent เลือกงานเองแบบกว้าง ผลคือรื้อใหม่, เพิ่มชั้นที่ไม่ได้ขอ, แตะหน้าอื่น
- **หลักฐาน**: SUTH helpdesk 09-04 (ขอ "ดีที่สุดในโลก" จนเกิดแผนเขียนใหม่ทั้งระบบ แล้วถอนเองเมื่อถามว่าจำเป็นหรือไม่), 09-19/09-23 (ออกแบบหน้าเข้าสู่ระบบแล้วไปแตะหน้าอื่น); RubricLens 08-09/08-17 (เพิ่มนโยบาย/คุกกี้แล้วถามว่าอันไหนไม่จำเป็น); Run-Performance (ขยายจากดึงข้อมูลเป็นหลายช่องทาง + ตัวชี้วัดอนุพันธ์ แล้วต้องตัดกลับหลายรอบ); ใช้คำระดับสูงสุดราว 40+ ครั้ง
- **ผลกระทบ**: สูงสุด เสียเวลาหลายสัปดาห์ โควตาหมดเร็ว working tree 29-42 ไฟล์ต้องแยกเป็นหลาย PR ความหงุดหงิดเพิ่ม
- **วิธีแก้ในคลัง**: กรอบขอบเขตใน `instructions/core.md` (ทำ / ไม่ทำ / เสร็จเมื่อ / หยุดเมื่อ), `playbook/triage.md` P5 (แปลงเป็นเกณฑ์ตรวจได้ไม่เกิน 5 ข้อ), `BACKLOG.md` ต่อรีโป, 1 issue = 1 branch = 1 PR, diff อยู่ใน ticket เท่านั้น (ที่เหลือลง BACKLOG; กฎ "ถามเมื่อแตะไฟล์เกิน N ไฟล์" ยังไม่มี (ข้อเสนอ)); ดู `research/06-prompting.md`
- **เช็กตัวเอง**: ถ้าลบคำว่า "ที่สุด/ระดับโลก" ออก ประโยคนี้ยังบอกได้ไหมว่าเสร็จเมื่อไร

## 2. ความต้องการ/การออกแบบแกว่งไปมา

- **อาการ**: สั่งกลับไปมาระหว่างวัน/สัปดาห์ (เพิ่ม แล้วลบ แล้วกู้คืน) หรือออกแบบหน้าเดิมซ้ำหลายรอบโดยไม่มีเกณฑ์รับ agent เดาว่าคำไหนชนะ
- **หลักฐาน**: SUTH helpdesk 09-05 ถึง 09-23 (หน้าเข้าสู่ระบบออกแบบใหม่อย่างน้อย 6 ครั้ง, prototype gate ตก 3 รอบ), 09-19 ถึง 09-24 (หน้าเปรียบเทียบ สร้าง -> ลบ -> กู้คืน, ตัวกรองแดชบอร์ดเปลี่ยนอย่างน้อย 5 ครั้ง, ตัวเลขหักเงินเปลี่ยนตามผู้ใช้งานระบบแก้ไข); Run-Performance 08-16 ถึง 09-29 (ใช้ agent สองตัว -> ตัวเดียว, ฟอร์มที่สร้างแล้วตัด, "ติดตั้ง skill pack แล้วลบ แล้วติดตั้งใหม่" ภายใน 24 ชม.); CAMPBANK 09-26 (ล็อกอินนิรนาม ไม่ -> ใช่)
- **ผลกระทบ**: สูง งานที่ตรวจผ่านแล้วต้องทำใหม่ ผู้ใช้สับสนเอง ("เริ่มงง ช่วยสรุป") และ agent ยอมรับว่าออกแบบผิดทิศ
- **วิธีแก้ในคลัง**: `prompts/04-change-requests.md` (04-C) (เดิม X -> ใหม่ Y แทนข้อไหน), ledger การตัดสินใจ `DECISIONS.md` (วันที่ / ที่มา / เงื่อนไขย้อนกลับ), brief ออกแบบ: เลือกอ้างอิง 1-3 อัน + เกณฑ์รับ + tokens ตรึง + ไม่เกิน 2 รอบรีวิว, ค่าเริ่มต้น "คงอันเดิมจนกว่าจะสั่งแทน"
- **เช็กตัวเอง**: ข้อนี้ขัดกับอะไรที่ฉันเคยตัดสินไว้ไหม และฉันเปิด DECISIONS.md ดูแล้วหรือยัง

## 3. คุณเป็นตัวส่งสารระหว่าง Codex กับ Claude (วนรีวิว 6-10 รอบ)

- **อาการ**: Claude เขียน -> คุณคัดลอกไปให้ Codex รีวิว -> คัดลอก finding กลับ -> "อนุมัติส่งกลับแก้" ซ้ำ โดย finding รอบหลังๆ เป็นเรื่องเล็ก (เช่น ความสะอาดของข้อความ error, จำนวนคำสั่งในเทสต์)
- **หลักฐาน**: Run-Performance platform (ก.ค.-ส.ค.) TASK-012 รวม 6 รอบ, TASK-017 รวม 10 รอบ, TASK-016 5 รอบ, ข้อความอนุมัติ/ส่งต่อราว 40 ข้อความ; SUTH helpdesk 08-11 (PR รีวิว/แก้/commit/push 4 พรอมต์ติดกัน), 09-14 ("โควตาจะหมด ส่งต่อให้ Claude")
- **ผลกระทบ**: สูง เป็นตัวกินเวลามากที่สุดของโปรเจกต์ platform และคุณทำหน้าที่ตัวส่งข้อความแทนระบบ
- **วิธีแก้ในคลัง**: `instructions/core.md` (review/fix ไม่เกิน 2 รอบ; BLOCKER ที่ยังเหลือหลังรอบ 2 = หยุดและรายงาน BLOCKED; SHOULD-FIX/COULD-FIX ลงรายงานและ `BACKLOG.md`), finding และ handoff เขียนเป็นไฟล์ใน repo แล้วส่งแค่ path + verdict 1 บรรทัด, มาโคร "ปิดงาน end-to-end" (`/ship`), `prompts/05-review-audit.md` (05-B) และ `/ship` (แก้ไม่เกิน 2 รอบ)
- **เช็กตัวเอง**: นี่คือรอบที่เท่าไร และ finding ที่เหลือมีข้อไหนเป็น BLOCKER จริง (ตามนิยามใน core)

## 4. ข้อมูลหายหลัง /clear หรือ compaction

- **อาการ**: หลัง `/clear`/`/compact` agent ไม่รู้ว่าตัดสินอะไรไปแล้ว ต้องถาม "เหลืออะไร" ใหม่ หรือข้อความรีวิวไม่เคยถึงอีกตัว และ agent ที่ซื่อสัตย์ไม่ยอมเดา (ถูกต้อง แต่เสียหนึ่งรอบ) handoff เก็บใน Temp/โฟลเดอร์ที่ไม่ commit
- **หลักฐาน**: SUTH helpdesk 09-07, 09-10, 09-15 (3 session ซ้ำ: `/clear` + `/compact` + "เหลืออะไร"), 09-17/09-19 (handoff ใน Temp); Run-Performance ก.ย. (หลัง compact, finding ปานกลาง 3 ข้อไม่เคยถึงผู้เขียน); SUTH 09-04 (context เต็มระหว่างงานรื้อใหญ่, compact 5 ครั้ง); practice-lab 08-17 (agent ไม่มีความจำของเฟสก่อนหน้า ตอบจาก git log)
- **ผลกระทบ**: กลาง-สูง เสียรอบ re-orient ทุกครั้ง ข้อตกลงหายจากสรุป
- **วิธีแก้ในคลัง**: `STATE.md` ระดับรีโป (งานปัจจุบัน / branch / ขั้นต่อไป / รออะไร), `/handoff-pack` (ทั้งฝั่งเขียนและฝั่งรับงาน; ผู้รับตรวจ git จริงก่อน), commit `wip: handoff` (STATE.md + HANDOFF.md) บน feature branch ก่อนส่งต่อ, เขียนไฟล์ก่อน `/clear` หรือ `/compact` ทุกครั้ง, หลีกเลี่ยง `/clear` กลางงาน (ใช้ `--continue`)
- **เช็กตัวเอง**: ถ้าเปิดแชทใหม่เดี๋ยวนี้ ไฟล์ใน repo บอก agent ได้ครบไหมว่าทำถึงไหน

## 5. ความลับหลุดในแชท (5 กรณี)

- **อาการ**: วางคีย์/รหัสผ่าน/PIN ลงในพรอมต์เพื่อให้ agent ใช้ต่อ หรือเปิดไฟล์ secret ใน IDE ขณะ agent ทำงาน (ไม่บันทึกค่าใดๆ ในไฟล์นี้)
- **หลักฐาน**: พบอย่างน้อย 5 กรณีในประวัติ: EQ-PROJECT 08-01 (คีย์ API บริการ AI), WebApp 07-02 (ข้อมูลล็อกอินสำหรับตั้งค่า), SUTH helpdesk 09-25 (รหัสผ่านผู้ดูแลระบบ), treadmill-sprint 07-08 (PIN), RubricLens 08-17 (คีย์ที่ต้องเปลี่ยนแทน) และตัวสแกน regex จับได้เพียง 1 ใน 5+
- **ผลกระทบ**: สูงมาก (ความเสี่ยงความปลอดภัย, ต้องหมุนเวียนคีย์) และตอนนี้ประวัติเก็บ 365 วัน ทำให้ความลับอยู่นานขึ้น
- **วิธีแก้ในคลัง**: `00-start-here.md` กติกาข้อ 5 (ห้ามวาง: ใช้ชื่อ env var แทน, บัญชีทดลอง, หมุนเวียนทุกอย่างที่เคยวาง, agent รายงานเฉพาะชื่อตัวแปร), สแกนด้วย gitleaks ทั้งไฟล์ปัจจุบันและประวัติ git (ตามข้อเสนอใน `research/07-review.md`), เก็บไฟล์ secret นอก workspace, `.env.example` ไม่มีค่าจริง; guard เป็นตัวเลือกที่ยังไม่ได้ติดตั้ง ดู [สถานะปัจจุบัน](../guardrails/README.md)
- **เช็กตัวเอง**: ข้อความที่กำลังจะวางมีค่าที่ใช้เข้าระบบจริงไหม ถ้ามี ให้วางเฉพาะชื่อตัวแปร

## 6. "อนุมัติหมด" แบบเช็คเปล่า

- **อาการ**: "อนุญาตทุกอย่าง / ไม่ต้องถามยืนยัน / ฉันไปนอนแล้ว / ทำ 1-7 จนเสร็จ" สลับกับรั้วเข้มงวด และขอปิดการถามสิทธิ์ (ขอวิธีอนุมัติทุกอย่าง 3+ ครั้ง)
- **หลักฐาน**: RubricLens 08-08/08-09/08-17 (อนุมัติ push+deploy ก่อนนอน); CAMPBANK 08-21; SUTH helpdesk 08-10 ถึง 09-04 (ราว 8 ครั้ง, "ให้ commit และ push ที่ main ตรงๆ" 09-04); codex-documents 09-29 (ส่งอีเมล 2 ฉบับโดยไม่มีการตรวจ, เลย์เอาต์ Canva เสียหาย); Run-Performance (ขอ auto-approve ทั้งหมด)
- **ผลกระทบ**: สูง ความเสี่ยงต่อฐานข้อมูลจริง ประวัติ git และไฟล์งานจริง ทั้งที่ AGENTS.md เขียนห้ามไว้ พฤติกรรมเดาไม่ได้ (บางครั้งเคารพ บางครั้งข้าม)
- **วิธีแก้ในคลัง**: `instructions/core.md` (Autonomy contract) (ทำเองได้: แก้ใน branch, test, commit, push feature branch + เปิด PR ตอน `/ship`/สั่งส่งมอบ; ถามก่อนเสมอ: merge, push main/master, deploy, ลบ, DB จริง, secret, บัญชีภายนอก, ส่งข้อความ; หยุดเมื่อ: เทสต์แดง 2 รอบ/ต้องเดา/เกินขอบเขต; จบด้วย "ที่แตะ"), auto mode + deny rules แทน bypass (`research/02-tool-mechanics.md`, `research/07-review.md`), branch protection จริงบน main; guard เป็นตัวเลือกที่ยังไม่ได้ติดตั้ง ดู [สถานะปัจจุบัน](../guardrails/README.md)
- **เช็กตัวเอง**: ถ้า agent ทำผิดที่สุดในกรอบที่ฉันอนุญาต ฉันยอมรับผลได้ไหม

## 7. Process/CI เกินตัวสำหรับทีม 1-2 คน

- **อาการ**: เพิ่ม AGENTS, CONTRIBUTING, ADR 20+ ฉบับ, skill ปิด issue, checkpoint ต่อ issue, CI + Nightly, pre-push รัน E2E เต็ม แล้วตัดแล้วขอกลับ แล้วตัดอีก; โปรเจกต์ไม่มีข้อมูลแต่ได้ระบบสำรอง/ACL/นโยบายระดับองค์กร
- **หลักฐาน**: SUTH helpdesk 09-10 (เขียนเองว่า workflow ซับซ้อนและทำให้ช้า, ลบ Actions วันเดียวกัน), 09-22 (push ค้างหลายนาทีจาก pre-push), 09-23 (ขอ Actions กลับ แล้ว "ตัด" อีก), GitHub account billing lock ทำให้ CI ล้มใน 2 วินาที; RubricLens 08-17 ("โปรเจกต์ไม่เก็บข้อมูล" แต่ได้ backup/privacy/cookie); CAMPBANK (monitoring + ตรวจ Safari 5 แบบ)
- **ผลกระทบ**: กลาง-สูง 4-8 พรอมต์ต่อ issue เวลารอ และการตัดสินใจกลับไปมา
- **วิธีแก้ในคลัง**: tier ของ workflow: demo / ใช้ภายใน / ใช้จริง พร้อมเช็กลิสต์ต่อ tier (`research/01-agent-workflows.md` + `stacks/hospital-web.md` (ระดับงาน)), คำสั่ง `verify` เดียว (unit + build + E2E เร็ว), DB test ตามสั่ง, รีวิวเดียว, ADR เฉพาะการตัดสินใจที่อยู่เกิน 30 วัน, เพิ่มกฎใหม่ได้ก็ต่อเมื่อกฎนั้นกันเหตุจริงได้
- **เช็กตัวเอง**: ขั้นตอนนี้กันเหตุจริงอะไรที่เคยเกิดขึ้นแล้ว หรือแค่ดูเป็นมืออาชีพ

## 8. ตรวจความเป็นไปได้ช้าเกินไป

- **อาการ**: เริ่มสร้างสถาปัตยกรรมใหญ่ก่อน แล้วค่อยรู้ว่าเข้าถึงข้อมูลไม่ได้ / ต้องใช้ฮาร์ดแวร์ที่ไม่มี / ข้อกำหนดไม่อนุญาต
- **หลักฐาน**: Run-Performance platform (ก.ค.-ส.ค.): เลือกสร้างแอปใหม่ก่อน แล้วค่อยพบว่า API ทางการของผู้ให้บริการอุปกรณ์ไม่อนุญาตสำหรับโปรเจกต์นักศึกษา (agent เตือนแล้วว่าใหญ่ราว 10 เท่า); 15+ task โครงสร้างพื้นฐานก่อนที่จะมีสิ่งให้กดใช้; D_ 08-11 (ถอดเสียงบน GPU ที่ไม่มี แล้วเลิก); Microbit-EQ 08-30/31 (ฮาร์ดแวร์ไม่มีวงตอบกลับ ทิ้งใน 3 เครื่องมือ)
- **ผลกระทบ**: กลาง-สูง งานหลายสัปดาห์ถูกพัก
- **วิธีแก้ในคลัง**: `prompts/01-start-project.md` (01-E) (ตาราง go/no-go: สิทธิ์เข้าถึงข้อมูล, ToS, การเก็บรหัสของคนอื่น, ค่าใช้จ่ายต่อเดือน, ภาระดูแล, ทางเลือกเล็กกว่า 10 เท่า), `CONSTRAINTS.md` ที่ agent อ่านทุก session, กฎ walking skeleton (ทุก 3 task ต้องมีของที่กดได้), `prompts/01-start-project.md` (01-A)
- **เช็กตัวเอง**: ข้อมูล/สิทธิ์/ฮาร์ดแวร์ที่งานนี้ต้องพึ่ง ฉันพิสูจน์แล้วหรือยังว่าใช้ได้จริง
