# 04 - คำขอเปลี่ยนและไอเดียใหม่

หลักการเรียงลำดับ: บั๊ก (ทำตามไฟล์ 03) -> ฟีดแบ็กที่บอกว่าไม่ตรงกับเกณฑ์เดิม (ถือเป็นบั๊ก) -> ฟีดแบ็กที่เปลี่ยนสิ่งที่ฟีเจอร์ควรทำ (คือ scope change, 04-C) -> ไอเดียใหม่ (04-A) -> ไอเดียที่โผล่กลางงาน (04-D ลง BACKLOG เท่านั้น)

หลักการ: ไอเดียไม่เข้ามาทำกลางงานโดยตรง ต้องผ่านการแยกประเภทก่อน เมื่อ skill `/new-request` พร้อมใช้ ให้ลองใช้แทน 04-A ถึง 04-C (skill: `triage`, `to-spec`)

---

## 04-A ไอเดียฟีเจอร์ใหม่

**ใช้เมื่อ:** นึกอะไรออกและอยากรู้ว่าควรทำไหม ทำแล้วกระทบอะไร
**ได้อะไร:** การประเมิน 1 หน้า: ควรทำ/รอ/ไม่ทำ พร้อมร่างเกณฑ์ตรวจรับและรายการที่ต้องเปลี่ยน ยังไม่แตะโค้ด

```text
ประเมินไอเดียนี้ ยังไม่ต้องทำ ไม่ต้องแก้ไฟล์
ไอเดีย: <บรรยายอิสระ ภาษาไทยได้>
ใครอยากได้และเพราะอะไร: <ผู้ใช้/หัวหน้า/ฉันเอง + ปัญหาที่เจอจริง>
ตัวตัดสินใจที่จะเปลี่ยนไป: <ฟีเจอร์นี้ช่วยให้ใครตัดสินใจอะไรต่างจากเดิม>

บริบท: อ่าน CONTEXT.md, decisions/ADR, .out-of-scope/ (ถ้ามี), BACKLOG.md และ spec ปัจจุบัน

ทำ
  1) ตรวจว่าซ้ำกับของที่มีอยู่ ขัดกับ ADR หรือเคยถูกปฏิเสธใน .out-of-scope/ หรือไม่ ถ้าใช่ ให้แสดงข้อนั้นก่อนอย่างอื่น
  2) บอกขนาด (S/M/L), ไฟล์/ส่วนที่จะเปลี่ยน, สิ่งที่ต้องย้ายหรือรื้อ
  3) ร่างเกณฑ์ตรวจรับ 3-5 ข้อที่ตรวจได้จริง ข้อความหน้าจอภาษาไทยให้เสนอเป็นตัวอักษรตรงๆ ให้ฉันอนุมัติ
  4) คำแนะนำ: ทำตอนนี้ / ลง BACKLOG / ไม่ทำ พร้อมเหตุผล
ไม่ทำ: ออกแบบเต็ม เขียนโค้ด สร้าง ticket (จนกว่าฉันตอบตกลง)

เห็นต่างได้: ถ้าไอเดียนี้ซับซ้อนเกินประโยชน์ หรือใช้ Excel/ขั้นตอนมือแก้ได้ถูกกว่า บอกตรงๆ
ความเสี่ยงที่ฉันไม่ได้ถาม: ข้อมูลผู้ป่วย/สิทธิ์ผู้ใช้ ภาระดูแลต่อ และผลต่อกำหนดส่งปัจจุบัน
เสร็จเมื่อ: ฉันได้คำแนะนำเดียวที่ตัดสินใจได้ภายใน 2 นาที
รายงานเป็นภาษาไทย: คำแนะนำ 1 บรรทัด / เหตุผล / ขนาด / เกณฑ์ตรวจรับร่าง / ความเสี่ยง
```

## 04-B ฟีดแบ็กจากผู้ใช้หรือไอที

**ใช้เมื่อ:** ได้ข้อความดิบจากแชท เสียง หรือเอกสารของคนที่ใช้ระบบ
**ได้อะไร:** แยกให้ว่าข้อไหนคือบั๊ก ข้อไหนคือเปลี่ยนความต้องการ ข้อไหนคือไอเดีย พร้อมชี้ข้อที่ขัดกับข้อตกลงเดิม

```text
ข้อความด้านล่างเป็นฟีดแบ็กจาก <ใคร / วันที่> เก็บต้นฉบับไว้ตามเดิม ห้ามแก้คำ ยังไม่ต้องลงมือ
เป้าหมาย: จัดประเภทฟีดแบ็กทีละข้อเพื่อให้ฉันตัดสินใจว่าจะทำอะไรก่อน
บริบท: ระบบ <ชื่อ>; ข้อตกลงเดิมอยู่ที่ <CONTEXT.md / decisions.md / spec>

ทำ: ตารางทีละข้อ
  id | ข้อความต้นฉบับย่อ | ประเภท (บั๊ก / ไม่ตรงเกณฑ์เดิม / เปลี่ยนความต้องการ / ไอเดียใหม่ / คำถาม) | เกี่ยวกับหน้าไหน | ขัดกับข้อตกลงเดิมข้อไหน (อ้าง id) | ต้องถามอะไร | ขนาด S/M/L | แนะนำ: ทำเลย / ตกลงก่อน / BACKLOG
ไม่ทำ: แก้โค้ด ตอบผู้ให้ฟีดแบ็กแทนฉัน สร้าง ticket

ข้อที่ตีความได้หลายแบบ ให้เสนอความหมายที่เป็นไปได้ 2-3 แบบ แล้วถามฉัน ห้ามเลือกเอง
ถ้าตัวเลขหรือกฎเงินในฟีดแบ็กไม่ตรงกับที่เคยตกลงไว้ (เช่น เปอร์เซ็นต์หัก ช่วงปีงบ) ให้ชี้ตรงๆ และถามว่าอันไหนถูก
ถามเฉพาะข้อที่ขวางงานจริง ไม่เกิน 8 ข้อ พร้อมคำตอบที่แนะนำ
เห็นต่างได้: ถ้าเห็นว่าฟีดแบ็กข้อไหนควรปฏิเสธหรือมีวิธีง่ายกว่า บอกเหตุผล
เสร็จเมื่อ: ทุกประโยคในต้นฉบับถูกจัดเข้าแถวในตารางอย่างน้อยหนึ่งแถว
รายงาน: ตาราง + คำถาม + ข้อเสนอลำดับทำ 3 อันดับแรก แล้วหยุดรอฉัน

--- ข้อความดิบ ---
<วางข้อความ ห้ามวางข้อมูลส่วนตัวของผู้อื่น>
```

## 04-C ขอเปลี่ยนขอบเขต (scope change)

**ใช้เมื่อ:** ของที่ตกลงและทำไปแล้วต้องเปลี่ยนความหมาย เช่น เดิมทำแบบ X ตอนนี้ต้องเป็น Y
**ได้อะไร:** ผลกระทบครบก่อนแก้ (ไฟล์ เทส เอกสาร ticket ที่ต้องทำใหม่) และการแก้ที่เริ่มหลังฉันยืนยัน

```text
เปลี่ยนข้อกำหนด
เดิม: <X> (อ้างที่มา: <ADR/decision/ticket id>)
ใหม่: <Y>   แทนข้อกำหนดเดิมเรื่องนี้ทั้งหมด
เหตุผล: <ใครเปลี่ยน เพราะอะไร วันที่>

ขั้นที่ 1 (ยังไม่แก้ไฟล์ รอฉันตอบ "ยืนยัน")
  - รายการผลกระทบ: ไฟล์, เทส, หน้าจอ, ข้อมูลเดิมที่ต้องย้าย, เอกสาร/ADR, ticket ที่ต้องเขียนใหม่
  - ของที่เคยทำเสร็จและตรวจแล้วจะถูกรื้ออะไรบ้าง และค่าใช้จ่ายที่เสียไป
  - ความเสี่ยง: ข้อมูลผู้ป่วย/การเงิน/สิทธิ์ และข้อตกลงเดิมที่จะขัดกัน
  - ทางเลือกที่เล็กกว่า (ทำบางส่วน / รอไว้ / ไม่เปลี่ยน) พร้อมข้อดีข้อเสีย
ขั้นที่ 2 (หลังฉันยืนยัน)
  - อัปเดต decisions.md/ADR ว่าอะไรถูกแทนที่ และเงื่อนไขการย้อนกลับ
  - แก้เฉพาะ ticket ที่ได้รับผลกระทบ ตามไฟล์ prompt 02-C

ไม่ทำ: ทำทั้งสองขั้นต่อกัน, แก้ส่วนที่ไม่อยู่ในรายการผลกระทบ, ลบหน้าหรือฟีเจอร์เดิมโดยไม่บันทึกเงื่อนไขการกู้คืน
เสร็จเมื่อ (ขั้นที่ 1): ฉันอ่านรายการผลกระทบแล้วตอบได้ว่ายืนยัน เลือกทางเล็ก หรือยกเลิก
เห็นต่างได้: ถ้าเห็นว่าการเปลี่ยนนี้ขัดกับสิ่งที่ตกลงไว้เพราะเหตุผลที่ยังใช้ได้ บอกตรงๆ ว่าควรถามผู้ขอเปลี่ยนอีกรอบ
รายงานเป็นภาษาไทย ไม่เกิน 1 หน้าจอ และปิดท้ายด้วยคำถามที่ฉันต้องตอบข้อเดียว
```

## 04-D "เพิ่มอันนี้ด้วย" กลางงาน (ส่งเข้า BACKLOG ไม่ทำทันที)

**ใช้เมื่อ:** ระหว่างทำ ticket อยู่ นึกอะไรออกหรือเห็นสิ่งที่ควรแก้
**ได้อะไร:** ไอเดียถูกจดบรรทัดเดียวลง BACKLOG.md และงานปัจจุบันเดินต่อโดยไม่บานปลาย

```text
ข้อนี้ไม่ต้องทำตอนนี้ ให้จดลง BACKLOG.md แล้วทำงานปัจจุบันต่อ
ไอเดีย: <บรรทัดเดียว>
ที่มา: <ฉันคิดเอง / ผู้ใช้ <ใคร> / agent สังเกตเห็น>

ทำ: เพิ่ม 1 แถวท้ายตารางใน BACKLOG.md ตามคอลัมน์ของตาราง template: # | Date | Source | Idea or feedback | Risk (P/A/M/-) | Triage (ใส่ unsorted) | Decision / reason (เว้นว่าง) | Issue link (เว้นว่าง) | Status (inbox) แล้วใส่ประเภทที่น่าจะเป็น (บั๊ก/ฟีเจอร์/หนี้เทคนิค) ไว้ในคอลัมน์ Idea (agent เพิ่มแถวนี้ได้เลยโดยไม่ต้องขออนุมัติ)
ไม่ทำ: แก้โค้ดที่เกี่ยวกับข้อนี้ สร้าง ticket ออกแบบ หรือเปลี่ยนแผนของ ticket ปัจจุบัน
ถ้าข้อนี้จริงๆ แล้วเป็นบั๊กที่เกิดจากงานปัจจุบันของเรา หรือเกี่ยวกับความปลอดภัยของข้อมูลผู้ป่วย ให้บอกฉันก่อนว่าไม่ควรรอ แล้วให้ฉันตัดสิน
เสร็จเมื่อ: เห็นบรรทัดใหม่ใน BACKLOG.md และงานเดิมเดินต่อจากจุดที่ค้าง
รายงาน 2 บรรทัด: จดแล้ว (ที่ไหน) และงานปัจจุบันอยู่ที่ขั้นไหน
```
