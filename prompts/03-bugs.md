# 03 - บั๊ก

ลำดับ: 03-A (รายงานบั๊ก) -> 03-B (วินิจฉัยอย่างเดียว) -> 03-C (แก้บั๊กที่ยืนยันแล้ว) ส่วน 03-D ใช้เมื่อระบบจริงมีปัญหาเร่งด่วน

หลักการ: ทำซ้ำให้ได้ก่อนแก้ แก้ที่สาเหตุ ไม่แก้เทสให้ผ่าน บั๊กอื่นที่เจอให้จดไว้ อย่าแก้รวม (skill: `diagnosing-bugs`, `tdd`)

---

## 03-A รายงานบั๊กและหาสาเหตุ

**ใช้เมื่อ:** เจออาการผิดปกติ และยังไม่รู้สาเหตุ อยากให้ agent จัดการตั้งแต่ทำซ้ำจนแก้ (บั๊กเล็กที่ไม่ซับซ้อน)
**ได้อะไร:** เทสที่พิสูจน์บั๊ก + การแก้ที่ต้นเหตุ + ผลทดสอบ ถ้าทำซ้ำไม่ได้จะหยุดและบอกว่าต้องการอะไร

```text
ใช้ skill diagnosing-bugs

บั๊ก
  อาการ: <สิ่งที่ผู้ใช้เห็น; ข้อความ error ตามต้นฉบับ / screenshot>
  อยู่ที่: <URL หรือหน้าจอ; ไฟล์หรือโมดูลถ้ารู้>
  ขั้นตอนทำซ้ำ: <ข้อ 1, 2, 3 หรือ "ไม่ทราบ">
  ควรเป็น / เป็นจริง: <บรรทัดละอย่าง>
  เริ่มเป็นตั้งแต่: <deploy / commit / เปลี่ยนข้อมูล / ไม่ทราบ>
  ผลกระทบ: <ใครใช้ไม่ได้ บ่อยแค่ไหน>
  ดูจาก: URL/พอร์ต <...> branch <...> (เพื่อกันตรวจผิดตัว)

เป้าหมาย: หาสาเหตุราก แก้ และพิสูจน์ว่าแก้แล้ว
ขอบเขต
  ทำ: 1) ทำซ้ำให้ได้ด้วยเทสที่แดงหรือ script 2) หาสาเหตุราก 3) แก้เล็กสุดที่ต้นเหตุ 4) รันเทสที่เกี่ยวข้องและ <npm run verify>
  ไม่ทำ: ซ่อน error, เขียนโค้ดเฉพาะกรณีเพื่อให้เทสผ่าน, แก้เทสเดิมให้ผ่าน, แก้บั๊กอื่นที่เจอ (ให้รายงานใน "พบเพิ่ม"), แตะข้อมูลจริง
ถ้าทำซ้ำไม่ได้: บอกสิ่งที่ลองและสิ่งที่ต้องการจากฉัน ห้ามเดาวิธีแก้

เสร็จเมื่อ: เทสใหม่แดงก่อนแก้และเขียวหลังแก้ (แสดงผลทั้งสองครั้ง) และ verify ทั้งชุดผ่าน
เห็นต่างได้: ถ้าเห็นว่าสิ่งที่ฉันเรียกว่าบั๊กเป็นพฤติกรรมตามที่ออกแบบ หรือสาเหตุน่าจะอยู่ที่ข้อมูล/สภาพแวดล้อม ให้บอกพร้อมหลักฐาน
รายงานเป็นภาษาไทย: 1) สาเหตุราก 1-2 ประโยค 2) ไฟล์ที่เปลี่ยน 3) หลักฐาน แดง->เขียน 4) สมมติฐาน 5) พบเพิ่มแต่ไม่ได้แก้ 6) ความเสี่ยงที่อาจมีบั๊กลักษณะเดียวกันที่อื่น
```

## 03-B วินิจฉัยอย่างเดียว (ห้ามแก้)

**ใช้เมื่อ:** อาการซับซ้อน ข้อมูลผิดปกติ หรือยังไม่แน่ใจว่าเป็นบั๊กจริงไหม (เช่น ตัวเลขไม่ตรง, ข้อมูลไม่ขึ้น)
**ได้อะไร:** ตารางหลักฐานแยกสาเหตุที่เป็นไปได้ พร้อมข้อเสนอแก้ 1-3 ข้อให้เลือก

```text
วินิจฉัยอย่างเดียว ห้ามแก้ไฟล์ ห้าม commit ห้ามเขียนข้อมูลจริง (อ่านอย่างเดียว; ถ้าต้องทดสอบเขียนให้ใช้ฐานชั่วคราวที่ตรวจ marker แล้วเท่านั้น)

เป้าหมาย: บอกว่าอาการนี้เกิดจากอะไร พร้อมหลักฐาน
อาการ: <สิ่งที่เห็น เช่น ยอดรวมหน้า A ไม่เท่าหน้า B / หน้าไม่รีเฟรชหลังแก้ไข>
บริบท: หน้า/endpoint <...>; ข้อมูลที่เกี่ยวข้อง <ช่วงเวลา / รายการ>; ลองแล้ว <...>

ตรวจตามลำดับและแยกสาเหตุให้ชัด: (ก) ข้อมูลต้นทางผิดหรือไม่ครบ (ข) ขั้นตอนบันทึก/นำเข้าผิด (ค) query หรือ logic การคำนวณผิด (ง) หน้าจอแสดงผิด/แคช/CORS/สถานะค้าง (จ) สภาพแวดล้อม เช่น เปิดเวอร์ชันเก่า
ทุกข้อสรุปต้องมีหลักฐาน: ไฟล์:บรรทัด หรือผลคำสั่ง หรือขั้นตอนทำซ้ำ ข้อที่ยังพิสูจน์ไม่ได้ให้ติด "ยังไม่ยืนยัน"
ข้อมูลเก่าหรือไม่ครบไม่ใช่หลักฐานว่าระบบพัง ให้ตรวจก่อนว่าต้นทางส่งมาหรือยัง

เสร็จเมื่อ: มีตารางสมมติฐาน | หลักฐานสนับสนุน | หลักฐานขัด | สถานะ (ยืนยัน/ตัดทิ้ง/ยังไม่ยืนยัน) และสมมติฐานที่เหลือมากที่สุดหนึ่งข้อ
เห็นต่างได้: ถ้าสมมติฐานของฉัน (<ที่ฉันคิดว่าเป็น>) ไม่สอดคล้องกับหลักฐาน บอกตรงๆ
รายงานเป็นภาษาไทย: สาเหตุที่น่าจะเป็น + ตาราง + ข้อเสนอแก้ 1-3 ข้อ (ผลกระทบ/ขนาดงาน/ความเสี่ยง) + สิ่งที่ยังไม่ได้ตรวจ แล้วหยุดรอฉันเลือกข้อ
```

## 03-C แก้บั๊กเดียวที่ยืนยันแล้ว

**ใช้เมื่อ:** หลัง 03-B ได้สาเหตุแล้ว และเลือกวิธีแก้แล้ว
**ได้อะไร:** แพตช์เล็กสุด + regression test + ยังไม่ commit ให้ตรวจก่อน

```text
แก้บั๊กเดียวเท่านั้น
หลักฐานที่ยืนยันแล้ว: <ข้อเท็จจริง 2-4 ข้อ จากผลวินิจฉัย>
วิธีแก้ที่เลือก: <ข้อที่ฉันเลือก>

ขอบเขต
  ทำ: 1) เขียน regression test ที่แดงก่อน 2) แก้เล็กสุดใน <ไฟล์/ฟังก์ชัน> 3) รัน targeted test แล้ว <npm run verify>
  ไม่ทำ: สำรวจทั้ง repo (ดูเฉพาะ <ไฟล์/ฟังก์ชัน>), แตะ <sync/schema/auth/scheduler>, แก้เทสเดิม, refactor, จัดรูปแบบไฟล์อื่น
  edge case อื่นที่เจอให้จดลง BACKLOG.md ไม่ต้องทำ
ถ้าการแก้ต้องแตะไฟล์นอกรายการหรือเปลี่ยน schema/auth ให้หยุดและถาม

เสร็จเมื่อ: เทสใหม่แดงก่อน เขียวหลัง, verify ทั้งชุดผ่าน, และ git diff มีเฉพาะไฟล์ที่เกี่ยวกับบั๊กนี้
ยังไม่ commit ให้ฉันดู diff ก่อน
เห็นต่างได้: ถ้าวิธีที่ฉันเลือกมีผลข้างเคียงหรือมีวิธีที่ดีกว่า บอกหนึ่งประโยคก่อนลงมือ แล้วรอฉันตอบถ้าผลข้างเคียงกระทบข้อมูล/สิทธิ์
รายงานเป็นภาษาไทย: แก้อะไร / หลักฐานแดง->เขียน / ผลกระทบที่เป็นไปได้ / สิ่งที่พบแต่ไม่ได้แตะ / สิ่งที่ยังไม่ได้ทดสอบ
```

## 03-D เหตุฉุกเฉินบนระบบจริง (production incident)

**ใช้เมื่อ:** ระบบที่ผู้ใช้จริงใช้อยู่ล่ม ข้อมูลผิดคน/ผิดรายการ หรืออาจมีข้อมูลรั่ว
**ได้อะไร:** ลำดับที่ปลอดภัย: ระงับผลกระทบ -> รวบรวมหลักฐาน -> เสนอการแก้ให้คุณอนุมัติ -> บันทึกเหตุการณ์ (เทียบกับ skill `engineering:incident-response`)

```text
มีเหตุในระบบจริง ให้จัดการตามลำดับ: ระงับผลกระทบก่อน วินิจฉัยทีหลัง
เหตุการณ์: <เกิดอะไร เมื่อไหร่ ใครแจ้ง>; ผลกระทบ: <ใคร กี่คน ข้อมูลอะไร>; ระบบ: <ชื่อ / เวอร์ชัน / เซิร์ฟเวอร์>
ประเภท: <ล่ม | ข้อมูลผิด | สิทธิ์ผิด/ข้อมูลรั่ว | ช้ามาก>

ขอบเขต (ทำได้เอง)
  - อ่าน log, config, โค้ด, git log ดูว่าเปลี่ยนอะไรล่าสุด
  - เสนอวิธีระงับ (rollback, ปิดหน้าที่เสี่ยง, ปิดระบบชั่วคราว) พร้อมผลข้างเคียง
ขอบเขต (ต้องรอฉันอนุมัติเป็นข้อๆ)
  - ทุกคำสั่งที่เปลี่ยนระบบจริง: restart, deploy, rollback, แก้ข้อมูล, รัน migration, เปลี่ยนสิทธิ์
  - การแจ้งใครภายนอก: ฉันเป็นคนแจ้งเอง ให้ร่างข้อความให้เท่านั้น
ไม่ทำ: แก้ข้อมูลจริงโดยไม่มีสำรอง, ลบ log, ใส่ secret ในไฟล์หรือแชท, เดาสาเหตุแล้วลงมือ

ลำดับ
  1) ประเมินความรุนแรงใน 3 บรรทัด และบอกว่าอาจมีข้อมูลผู้ป่วยรั่วหรือไม่ (ถ้าอาจรั่ว ให้บอกขั้นตอนที่ฉันต้องแจ้งผู้รับผิดชอบด้านไอที/PDPA ทันที)
  2) ทางระงับที่เร็วและย้อนกลับได้ ให้ฉันเลือก
  3) หลังระงับแล้วค่อยวินิจฉัยสาเหตุราก (ใช้ skill diagnosing-bugs) โดยแยกหลักฐานจากข้อสันนิษฐาน
  4) ร่างบันทึกเหตุการณ์ docs/incidents/<วันที่>.md: ลำดับเวลา, สาเหตุ, ผลกระทบ, สิ่งที่ทำ, วิธีป้องกัน

เสร็จเมื่อ: ระงับผลกระทบได้และยืนยันด้วยหลักฐาน (เช่น ผล curl หรือ screenshot) ไม่ใช่แค่บอกว่าน่าจะดีขึ้น
เห็นต่างได้: ถ้าเห็นว่าควรปิดระบบชั่วคราวแต่ฉันเลือกทางอื่น บอกความเสี่ยงตรงๆ
ทุกครั้งที่ตอบให้เริ่มด้วยสถานะ 1 บรรทัด (ระงับแล้ว / กำลังระงับ / ยังไม่ทราบ) และสิ่งที่รอฉันอนุมัติ
```
