# 01 - เริ่มโปรเจกต์ใหม่

เริ่มด้วย `/ask-matt` ถ้ายังไม่รู้เส้นทาง หรือ `/grill-with-docs` ใน repo; prompts เป็น recipes อ้างอิง ไม่ใช่ router เพิ่ม ลำดับที่แนะนำ: 01-A (คุยก่อน) -> 01-B (รับความต้องการ) -> 01-C (เลือกระดับงาน) -> 01-D (เลือก stack) -> 01-E (feasibility ถ้ามีข้อมูลหรือสิทธิ์จากภายนอก) -> จบด้วย `/to-spec` แล้ว `/to-tickets`

หลักการ: ยังไม่เขียนโค้ดจนกว่าจะล็อกชื่อ/ระดับงาน/stack/ขอบเขตได้ ทุก prompt ด้านล่างสั่งให้ agent เห็นต่างและชี้ความเสี่ยงที่คุณอาจมองข้าม

---

## 01-A คุยก่อน ยังไม่ต้องทำ

**ใช้เมื่อ:** มีไอเดียระบบใหม่ แต่ยังไม่รู้ว่าจะเริ่มยังไง
**ได้อะไร:** สรุปที่ agent เข้าใจ + บล็อกเกอร์ที่มองข้าม + คำถามไม่เกิน 5 ข้อ โดยไม่มีไฟล์ถูกสร้าง

```text
คุยกันก่อน ยังไม่ต้องเขียนโค้ด ไม่ต้องติดตั้งอะไร ไม่ต้องสร้างไฟล์

เป้าหมาย: ฉันอยากทำ <ระบบอะไร> ให้ <ผู้ใช้: บทบาท/จำนวนคน> เพื่อ <ผลลัพธ์ที่ต้องการ>
บริบท: <ตอนนี้ทำงานนี้ด้วยวิธีไหน เช่น Excel / กระดาษ>; ข้อมูลอ่อนไหว: <มี/ไม่มี เช่น ข้อมูลผู้ป่วย>
ข้อจำกัดที่รู้แล้ว: <งบ / ต้องรันบนเซิร์ฟเวอร์โรงพยาบาล / เวลาที่มี / ใครช่วยได้จริง>

ขอบเขตของ session นี้
  ทำ: ฟัง สรุป ตั้งคำถาม เสนอทางเลือก
  ไม่ทำ: สร้างไฟล์ เลือก stack ขั้นสุดท้าย สร้าง repo

ให้ตอบตามลำดับ
1) สรุปสิ่งที่เข้าใจไม่เกิน 5 บรรทัด ให้ฉันยืนยัน
2) บล็อกเกอร์หรือความเสี่ยงที่ฉันอาจมองข้าม (ข้อมูลผู้ป่วย/PDPA, สิทธิ์เข้าถึงข้อมูลจากระบบอื่น, คนดูแลหลังส่งมอบ, นโยบายไอทีโรงพยาบาล)
3) ถ้าเห็นว่าไอเดียนี้ใหญ่เกินไปหรือมีวิธีที่เล็กกว่า ให้บอกตรงๆ พร้อมเหตุผล
4) ถามฉันไม่เกิน 5 ข้อ เฉพาะข้อที่คำตอบต่างกันแล้วงานต่างกันมาก พร้อมคำตอบที่คุณแนะนำ
5) ข้อที่ไม่รู้ให้บอกว่าไม่รู้ ห้ามเดา

เสร็จเมื่อ: ฉันตอบคำถามครบแล้วและยืนยันสรุปในข้อ 1
รายงานเป็นภาษาไทย (ศัพท์เทคนิคเป็นอังกฤษได้) ปิดท้ายด้วยข้อเสนอว่าควรไป prompt 01-B หรือ /grill-with-docs
```

## 01-B รับความต้องการ (requirement intake)

**ใช้เมื่อ:** มีคำพูดดิบจากผู้ใช้/ไอที/หัวหน้า หรือ voice transcript ยาวๆ
**ได้อะไร:** ตารางความต้องการทีละข้อ พร้อมข้อที่ขัดกันและคำถามที่ขวางงานจริง เก็บต้นฉบับไว้ไม่แก้

```text
ข้อความด้านล่างมาจาก <ใคร / วันที่> เก็บต้นฉบับไว้ตามเดิมในไฟล์ docs/requirements/raw-<วันที่>.md ห้ามแก้คำ
ยังไม่ต้องลงมือทำระบบ

เป้าหมาย: แปลงข้อความดิบเป็นความต้องการที่ตรวจสอบได้ทีละข้อ
บริบท: ระบบ <ชื่อ> ผู้ใช้หลักคือ <บทบาท>; ข้อตกลงเดิมอยู่ที่ <GLOSSARY.md / decisions.md ถ้ามี>

ขอบเขต
  ทำ: แยกข้อ จัดหมวด ตรวจว่าขัดกับข้อตกลงเดิมหรือไม่
  ไม่ทำ: ออกแบบหน้าจอ เขียนโค้ด ตัดสินใจแทนฉันในเรื่องที่ตีความได้หลายแบบ

ผลลัพธ์เป็นตาราง: id | ความต้องการ (1 ประโยค) | ใครต้องการ | หน้า/ฟีเจอร์ที่เกี่ยว | ขัดกับข้อตกลงเดิมข้อไหน | วิธีตรวจว่าเสร็จ | ขนาด (S/M/L)
แล้วแยกเป็น 4 กลุ่ม: (A) ทำได้เลย (B) ต้องถามก่อน (C) ความคิด "ไว้ทีหลัง" ให้ลง BACKLOG.md ไม่ทำ (D) ข้อจำกัดหรือความชอบที่ผู้พูดบอก

ถามเฉพาะข้อที่ขวางงานจริง ไม่เกิน 8 ข้อ พร้อมคำตอบที่คุณแนะนำ
เห็นต่างได้: ถ้าข้อไหนฟังดูไม่สมเหตุผลหรือเสี่ยงต่อข้อมูลผู้ป่วย/ตัวเลขการเงิน ให้บอกเหตุผล และความเสี่ยงที่ผู้พูดอาจไม่ได้นึกถึง
รายงาน: ตาราง + 4 กลุ่ม + คำถาม แล้วหยุดรอฉันตอบ "ตกลง"

--- ข้อความดิบ ---
<วางข้อความ>
```

## 01-C เลือกระดับงาน (demo / ใช้ภายใน / ใช้จริง)

**ใช้เมื่อ:** ก่อนเริ่มสร้าง เพื่อไม่ให้ทำ process หนักเกินจริงหรือเบาเกินไป
**ได้อะไร:** คำแนะนำระดับงานพร้อม checklist ที่ต้องมี/ไม่ต้องมี ตามระดับนั้น

```text
เป้าหมาย: ช่วยฉันเลือกระดับงานของ <ชื่อโปรเจกต์> ระหว่าง
  demo (โชว์ / พอร์ตโฟลิโอ ไม่มีข้อมูลจริง)
  ใช้ภายใน (คนในหน่วยงานใช้ มีข้อมูลจริงบางส่วน)
  ใช้จริง (ข้อมูลผู้ป่วยหรือการเงิน ต้องรับผิดชอบระยะยาว)

บริบท: ผู้ใช้ <ใคร กี่คน>; ข้อมูลที่จะเก็บ <ชนิด>; รันที่ <เครื่อง/เซิร์ฟเวอร์/cloud>; คนดูแลต่อ <ใคร หรือยังไม่มี>; กำหนดส่ง <วันที่>

ขอบเขต
  ทำ: ตอบเป็นตาราง ระดับที่แนะนำ + เหตุผล 3 ข้อ + สิ่งที่ "ต้องมี" และ "ข้ามได้" (test, backup, audit log, สิทธิ์ผู้ใช้, CI, เอกสารส่งมอบ, monitoring)
  ไม่ทำ: สร้างไฟล์หรือ config ใดๆ

เห็นต่างได้: ถ้าฉันเลือกระดับต่ำกว่าที่ข้อมูลจริงต้องการ ให้บอกตรงๆ ว่าความเสี่ยงคืออะไร
ถ้ามีข้อมูลผู้ป่วยแม้เพียงเล็กน้อย ให้ถือว่าต้องเป็น "ใช้จริง" ในส่วนที่แตะข้อมูลนั้น และบอกว่าแยกส่วนได้หรือไม่

เสร็จเมื่อ: มีตารางระดับงานที่ฉันยืนยันได้ และระบุว่าจะบันทึกไว้ใน AGENTS.md บรรทัดไหน
รายงาน: คำแนะนำ 1 บรรทัด + ตาราง + ความเสี่ยงที่ฉันอาจมองข้าม + สิ่งที่ฉันต้องตัดสินใจ
```

## 01-D ตัดสินใจ stack พร้อมค้นคว้า

**ใช้เมื่อ:** ต้องเลือก framework / ฐานข้อมูล / hosting และอยากได้ข้อมูลล่าสุดที่อ้างอิงได้
**ได้อะไร:** ตารางเปรียบเทียบ 2-3 ทางเลือก พร้อมแหล่งอ้างอิงและวันที่ + คำแนะนำหนึ่งทางและร่าง ADR — ใช้ `grill-with-docs` ระบุข้อจำกัด แล้ว `research` ตอบจากแหล่งหลัก (prompt ด้านล่างใช้เมื่ออยากคุมรายละเอียดเอง)

```text
ใช้ skill research ตอบคำถามนี้ วันที่วันนี้: <YYYY-MM-DD>
คำถาม: โปรเจกต์ <ชื่อ> ระดับงาน <demo | ใช้ภายใน | ใช้จริง> ควรใช้ stack ไหนระหว่าง <ตัวเลือก A / B / C>
การตัดสินใจนี้จะใช้: <เลือก stack แล้วเริ่มสร้าง repo>
ข้อจำกัดที่ยืนยันแล้ว: <ต้องติดตั้งบนเซิร์ฟเวอร์โรงพยาบาล / ฟรีก่อน / ทีมรู้จัก Vue+Express+MySQL อยู่แล้ว / ฯลฯ>

กติกา
  - ค้นเว็บสำหรับเรื่องที่เปลี่ยนได้ (เวอร์ชัน ราคา โควตา การรองรับ) แม้รู้สึกว่ามั่นใจ
  - ใช้แหล่งหลักก่อน: เอกสารทางการ บล็อกวิศวกรรมของผู้ให้บริการ มาตรฐาน; จัดระดับ T1 หลัก / T2 ผู้เชี่ยวชาญ / T3 อื่นๆ
  - ทุกข้อเท็จจริงต้องมี URL ผู้เขียนหรือองค์กร และวันที่ ห้ามแต่ง URL; เปิดไม่ได้ให้ติด UNVERIFIED
  - อ้างคำพูดตรงไม่เกิน 15 คำ นอกนั้นสรุปเอง
  - ถ้าตัวเลือกที่ฉันคุ้นเคยอยู่แล้ว (<stack เดิม>) ใช้ได้พอ ให้บอกตรงๆ ว่าไม่ต้องเปลี่ยน อย่าเสนอของใหม่เพื่อความน่าสนใจ
  - หยุดค้นเมื่อข้อมูลใหม่ไม่เปลี่ยนข้อสรุป และบอกเหตุผลที่หยุด

ขอบเขต: ค้นและเขียนสรุปลง docs/research/stack-<วันที่>.md เท่านั้น; ไม่ติดตั้ง ไม่สร้างโปรเจกต์
รายงาน
  1) คำตอบไม่เกิน 10 บรรทัด + ระดับความมั่นใจ
  2) ตาราง: ข้อเท็จจริง | แหล่ง | วันที่ | ระดับ
  3) ต้นทุนการเปลี่ยนใจภายหลัง (reversal cost) ของแต่ละทาง
  4) สิ่งที่ยังไม่รู้ และอะไรจะทำให้เปลี่ยนคำตอบ
  5) ความเสี่ยงที่ฉันไม่ได้ถาม (ภาระดูแล, การส่งมอบให้ไอทีโรงพยาบาล, ข้อมูลออกนอกองค์กร)
เสร็จเมื่อ: ไฟล์ research ถูกเขียนและทุกแถวในตารางมี URL + วันที่ หรือถูกติดป้าย UNVERIFIED
```

## 01-E ประตู feasibility ก่อนออกแบบ

**ใช้เมื่อ:** ระบบต้องพึ่งข้อมูลหรือสิทธิ์จากภายนอก (API ของระบบโรงพยาบาลอื่น, HIS, บริการ cloud ที่ต้องอนุมัติ)
**ได้อะไร:** ตาราง go / no-go หนึ่งหน้า ก่อนเสียเวลาออกแบบ

```text
ก่อนออกแบบหรือสร้างอะไร ตรวจว่าทำได้จริงไหม ยังไม่เขียนโค้ด

เป้าหมาย: ตาราง go/no-go ของ <ชื่อโปรเจกต์> ที่ฉันตัดสินใจได้ภายใน 5 นาที
บริบท: ต้องใช้ข้อมูล/สิทธิ์จาก <ระบบหรือบริการภายนอก>; ฉันเป็น <นักศึกษาฝึกงาน / ไม่มีสิทธิ์ admin ของระบบนั้น>

ตรวจ: (1) ฉันมีสิทธิ์เข้าถึงข้อมูลนั้นจริงหรือไม่ และใครเป็นคนอนุมัติ (2) ข้อกำหนดการใช้งานและนโยบายไอทีโรงพยาบาล/PDPA (3) ต้องเก็บรหัสผ่านหรือ token ของคนอื่นหรือไม่ (4) ค่าใช้จ่ายต่อเดือน (5) ภาระดูแลหลังสร้าง ชั่วโมงต่อสัปดาห์ (6) ทางเลือกที่เล็กกว่า 10 เท่าที่ยังแก้ปัญหาเดิม

ขอบเขต: อ่าน/ค้นเท่านั้น; ข้อที่ยืนยันไม่ได้ให้ติด "ยังไม่ยืนยัน" ห้ามเดา
เห็นต่างได้: ถ้าเห็นว่าควรหยุด ให้ฟันธงว่า no-go พร้อมเหตุผลและทางเล็กสุด
เสร็จเมื่อ: ทุกข้อมีสถานะ ยืนยันแล้ว / ยังไม่ยืนยัน / ต้องถามใคร
รายงาน: verdict 1 บรรทัด + ตาราง + ข้อจำกัดที่ยืนยันแล้ว (ให้บันทึกลง CONSTRAINTS ใน AGENTS.md)
```
