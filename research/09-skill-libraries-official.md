### 1.3 Conventions worth copying (each with source)
1. **Two invocation classes, decided on purpose.** User-invoked = `disable-model-invocation: true` (Claude) plus `policy.allow_implicit_invocation: false` in `agents/openai.yaml` (Codex); description is a one-line human summary without trigger lists. Model-invoked = rich "Use when..." triggers. Source: `.agents/invocation.md` (https://raw.githubusercontent.com/mattpocock/skills/main/.agents/invocation.md, T2, accessed 2026-10-01) and local `writing-for-agents/SKILL-MECHANICS.md` (T2, read 2026-10-01): "If it only ever fires by hand, make it user-invoked and pay no context load." The vault's `ship` already does this for Claude but has no `agents/openai.yaml`, so Codex may still auto-invoke it (UNVERIFIED for the installed Codex version).
2. **Skills call skills explicitly, and user-invoked skills cannot be called by other skills.** Rule from `.agents/invocation.md`: use an explicit Skill-tool call for a model-invoked dependency; for a user-invoked one, tell the human to run it. Relevant to `ship`, which says "Use the implement/tdd skills if installed" (both are manual-only in the local copy, so the model cannot reach them).
3. **One router skill for the human.** `ask-matt` maps every user-invoked skill and when to use it, and repo `CLAUDE.md` requires it to be updated whenever a skill is added, renamed or removed. Plus `PHASE-BOUNDARIES.md`, an ordered decision tree (Continue, then /clear, then /handoff, then subagent, then /compact). Source: repo CLAUDE.md (https://raw.githubusercontent.com/mattpocock/skills/main/CLAUDE.md) and local `C:\Users\wayuo\.agents\skills\ask-matt\SKILL.md`. The vault's equivalent is `00-start-here.md` (a table, not a skill), which is fine, but nothing keeps it in sync with `skills/`.
4. **A setup skill that is prompt-driven, not a script.** `setup-matt-pocock-skills`: explore the repo, present findings, lead each question with the recommended answer, confirm a draft, then write a `## Agent skills` block into the existing `CLAUDE.md` or `AGENTS.md` (never create the other) and seed files under `docs/agents/`. Seed templates live as sibling files in the skill folder. Source: local SKILL.md (read 2026-10-01). ADR 0001: only hard-dependency skills (`to-tickets`, `to-spec`, `triage`) say "run /setup-matt-pocock-skills if not provided"; soft ones degrade gracefully (https://raw.githubusercontent.com/mattpocock/skills/main/.agents/adr/0001-explicit-setup-pointer-only-for-hard-dependencies.md, T2).
5. **No separate "verify" tool; ask the same prompt-driven skill to check drift.** `.out-of-scope/setup-skill-verify-mode.md`: "check my existing files against current seed templates and report drift" (https://raw.githubusercontent.com/mattpocock/skills/main/.out-of-scope/setup-skill-verify-mode.md, T2).
6. **`.out-of-scope/` as institutional memory.** Each rejected request gets a short file with reasoning and the issue numbers that asked (example `question-limits.md` cites #44 "Codex just asked me 200 questions"). Source: https://raw.githubusercontent.com/mattpocock/skills/main/.out-of-scope/question-limits.md (T2). The vault's `playbook/triage.md` P5/P6 inbox has no equivalent "decided no" list; `new-request` Step 3 does search "already decided, rejected" but there is no standard place for rejections other than `DECISIONS.md`.
7. **Bucketed repo with a promotion rule.** Only `engineering/` and `productivity/` appear in README and `plugin.json`; `misc/`, `in-progress/`, `deprecated/` do not. `scripts/link-skills.sh` links `in-progress/` locally because "this local install is exactly where that feedback loop runs" but excludes `misc/` and `deprecated/`. Source: repo CLAUDE.md and `link-skills.sh` (T2).
8. **Style rule enforced in repo docs.** "No em-dashes anywhere in repository prose" (repo CLAUDE.md). Trivial but shows a mechanical, checkable style rule.
9. **Docs page per promoted skill with a fixed template** ("What it does", "When to reach for it", "Common questions", "It's working if"); the "It's working if" bullets "must be verifiable without consulting the skill's implementation"; common questions come from real issues, not invented. Source: `.agents/writing-docs.md` (https://raw.githubusercontent.com/mattpocock/skills/main/.agents/writing-docs.md, T2). The "It's working if" idea is a cheap acceptance test for our skills.
10. **`retro` skill (new on main, not in the local copy).** After a session, review the session log and propose environment improvements in categories: Navigation, Automated checks, Coding standards, Global AGENTS.md, Tool economy, No-ops, Information access; prefers automating deterministic rules over writing instructions. Source: https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/retro/SKILL.md (T2, summary of fetch). This maps directly onto the vault's `me/pitfalls.md` + monthly review loop.
11. **`pr` skill (new on main).** PR body = Summary (minimal visual), Evidence (before/after, screenshots first), Merge Danger (one-way vs two-way door, blast radius). Source: https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/pr/SKILL.md (T2). `ship` Step 5 lists "summary, acceptance criteria with evidence, how to test, risks, screenshots" but has no reversibility field.
12. **`writing-for-agents` is the authoring standard** (installed locally, T2): context pointers ("the pointer's wording, not its target, decides when the agent reaches the material"), two loads (context vs cognitive), information hierarchy / progressive disclosure, completion criteria that are "checkable and exhaustive", leading words, negation failure mode ("prompt the positive"), pruning: single source of truth, the environment is a source of truth (a document restating it is a cache), hunt no-ops. Read in full at `C:\Users\wayuo\.agents\skills\writing-for-agents\SKILL.md`.

### 2.2 Skill authoring best practices (T1)
Source: https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices (no date shown; accessed 2026-10-01). Concrete rules:
- Concise: "The context window is a public good"; add only what Claude does not already know.
- Degrees of freedom: high (text) for judgement tasks, low (exact script, "do not modify the command") for fragile operations such as migrations.
- `name` max 64 chars, lowercase/digits/hyphens, no reserved words "anthropic"/"claude". Gerund names recommended (`processing-pdfs`); avoid `helper`, `utils`, inconsistent patterns.
- `description` max 1,024 chars, non-empty, no XML tags, **third person** ("Processes Excel files..."), says what it does AND when to use it, includes key terms. It is injected into the system prompt; Claude picks among "potentially 100+" skills from it.
- Body under 500 lines; references one level deep from SKILL.md; reference files over 100 lines get a table of contents; name files descriptively; forward slashes only (even on Windows).
- Workflows: numbered steps with a copyable checklist; feedback loops (validate, fix, repeat); plan-validate-execute for destructive or batch work; verbose validator errors.
- Avoid time-sensitive text (use an "Old patterns" section); one term per concept; give a default rather than five options; examples as input/output pairs.
- Evaluation-driven development: run representative tasks WITHOUT the skill first, note failures, write **three** scenarios, baseline, write minimal instructions, iterate. Eval shape: `{"skills": [...], "query": ..., "files": [...], "expected_behavior": [...]}`. Docs say "There is not currently a built-in way to run these evaluations" in this page (superseded for Claude Code plugins by `claude plugin eval`, see 2.4).
- "Claude A / Claude B" loop: one instance writes the skill, a fresh instance uses it on real tasks, observe navigation (unexpected reads, ignored files, overused sections), feed back.
- Test with Haiku, Sonnet and Opus. Checklist at the end of the page (core quality, code, testing: at least three evals, three models, real usage).

### 2.3 Claude Code skills reference (T1)
Source: https://code.claude.com/docs/en/skills (accessed 2026-10-01; fetched through a summariser, so exact flags should be re-checked with `/doctor` or `claude --help` before relying on them).
- Locations and precedence: enterprise > personal `~/.claude/skills` > project `.claude/skills` > nested > plugin. "A `<skill-name>` entry can be a symlink to a directory elsewhere" (loaded once even if two paths point to it). Live change detection within a session; new top-level skills folder needs `/reload-skills`.
- Frontmatter beyond the spec: `when_to_use`, `disable-model-invocation`, `user-invocable: false`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork` + `agent`, `paths`, `shell: bash|powershell`, `hooks`, `argument-hint`, `arguments`, plus spec fields `license`, `compatibility`, `metadata` (accepted, not acted on).
- Limits that matter: `description` + `when_to_use` truncated at **1,536 characters** per skill; listing budget is **1% of the context window**; when it overflows, least-used skills lose their descriptions. After auto-compaction the most recent invocation of each skill is re-attached with its first **5,000 tokens**, total budget 25,000, so "put most important instructions at top of SKILL.md".
- Controls: `skillOverrides` in settings (`on`, `name-only`, `user-invocable-only`, `off`); `/skill-doctor` (cost and usage; flags skills never invoked); `/doctor`; `claude plugin validate .claude/skills` (v2.1.233+) to validate SKILL.md.
- "Missed rule every time: move to hook" and "Skill triggers too often: more specific description or `disable-model-invocation: true`".
- Windows: `shell: powershell` supported for injected commands; `${CLAUDE_SKILL_DIR}` resolves the skill folder.
- Disagreement noted: agentskills spec and Claude platform say description <= 1,024 chars; Claude Code reads up to 1,536 (combined with `when_to_use`). Trust the stricter 1,024 for portability across Claude and Codex.

### 2.4 Plugins, marketplaces, versioning, evals (T1)
Sources (all https://code.claude.com/docs/en/..., accessed 2026-10-01): `plugins` (overview), `plugins/create-marketplace`, `plugins/host-marketplace`, `plugins/install`, `plugin-evals`, `plugins/measure`.
- A plugin = directory with `.claude-plugin/plugin.json` plus `skills/`, `agents/`, `hooks/`, `.mcp.json`. Skills in plugins are namespaced `/plugin-name:skill`, so `/ship` would become `/<plugin>:ship`. "Use a plugin when you want several skills, subagents, hooks... packaged as one unit"; standalone `~/.claude/skills` is documented as fully supported otherwise.
- Marketplace = repo with `.claude-plugin/marketplace.json` (`name`, `owner`, `plugins[]` with `name` + `source`). Commands: `claude plugin validate ./my-marketplace`, `claude plugin marketplace add ./my-marketplace` (local dir), `claude plugin install <name>@<marketplace>`, `claude plugin list`, `claude plugin details <name>`. Local-directory marketplace: "Claude Code reads the plugin's files directly... edits take effect at the next session start or `/reload-plugins`, with no change to the plugin's `version`". Hosted: `claude plugin marketplace add <owner>/<repo>`; pin with `#<ref>`; `--scope project` writes `.claude/settings.json` to commit.
- Versioning: users get a new copy only when computed version changes ("plugin.json first, then marketplace entry"). Either bump `version` each release or omit it and track commits. Setting version in both places is flagged by `validate`. Renames use a `renames` map (append-only); no deprecation state. Release channels = two marketplaces pointing at different refs. Third-party marketplaces have auto-update OFF by default; official marketplace auto-update ON.
- Cost measurement: `claude plugin details <name>` prints **Always-on** tokens (name + description + when_to_use per skill/agent/command) and per-component rows; official-marketplace plugins show "Context cost" before install; "Not used recently" after 14 days and 10 sessions.
- Evals: `claude plugin eval init` (writes cases) and `claude plugin eval .` run a suite from `evals/<case>/prompt.md` + `graders/*.md`. Each case runs **3 times** by default; pass at `--threshold` (default 1.0); six grader types: `regex`, `tool_used`, `tool_order`, `file_exists` (free) and `llm`, `baseline` (judge model); `tool_used: Skill` grader checks the skill actually fired; baseline comparison gives a delta for "with vs without plugin"; exit code 1 below threshold, usable in CI; costs real tokens. The page says the skill-creator plugin uses a different `evals/evals.json` format and "neither tool reads the other's case files". It only works on a plugin, so using it means packaging the vault as a plugin.
- Security: plugin code "can run with your user privileges"; review before install (https://code.claude.com/docs/en/plugins/security, linked from the pages above, not fetched).

### 2.7 Memory and CLAUDE.md (T1)
Source: https://code.claude.com/docs/en/memory (accessed 2026-10-01).
- "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook" (the vault's `guard.mjs` already follows this).
- Target **under 200 lines per CLAUDE.md**; concrete, verifiable wording; `@path` imports load at launch and do NOT reduce context cost (max depth 4 hops); multi-step procedures and part-of-codebase rules belong in skills or `.claude/rules/` with `paths:` frontmatter.
- AGENTS.md: Claude Code (v2.1.277+) reads `AGENTS.md` directly only when no `CLAUDE.md`/`CLAUDE.local.md` exists in or above the working dir; otherwise use `@AGENTS.md` inside CLAUDE.md. Symlink `CLAUDE.md -> AGENTS.md` is discouraged on Windows (needs admin/Developer Mode, Git checks it out as text). Setting `claude-md-and-agents-md` in `/config` loads both.
- `/doctor prompt-audit` (v2.1.283+) audits CLAUDE.md, AGENTS.md, rules, skills, commands and subagents for outdated, contradictory or non-existent references and proposes edits without applying them. `/doctor` also proposes trims (cuts what Claude can derive from the codebase, keeps pitfalls, rationale, non-default conventions).
- Block HTML comments in CLAUDE.md are stripped before injection (free maintainer notes). `/memory`, `/context` show what loaded. Auto memory: `MEMORY.md` first 200 lines or 25 KB loaded each session.
- Fit for the vault: `~/.claude/CLAUDE.md` is already a one-line `@D:/ai-playbook/instructions/core.md` import (valid, depth 1). `core.md` is the always-loaded cost on every turn; keep it short and move procedures into skills.

## 4. agentskills.io spec and tooling, and `npx skills`

### 4.1 Spec (T1 for the open standard)
Source: https://agentskills.io/specification (accessed 2026-10-01; no date shown). Repo agentskills/agentskills: 25,822 stars, 1,950 forks, Apache-2.0, created 2025-12-16, last push 2026-08-09 (https://api.github.com/repos/agentskills/agentskills, accessed 2026-10-01).
- Layout: `skill-name/SKILL.md` required; optional `scripts/`, `references/`, `assets/`.
- Frontmatter: `name` (1-64 chars, lowercase alnum + hyphens, no leading/trailing/double hyphen, **must match the parent directory name**), `description` (1-1024 chars, what + when, keywords), optional `license`, `compatibility` (<= 500 chars), `metadata` (string-to-string map, e.g. `author`, `version: "1.0"`), `allowed-tools` (space-separated, experimental).
- Progressive disclosure budget: metadata ~100 tokens per skill at startup; instructions "< 5000 tokens recommended"; "Keep your main SKILL.md under 500 lines"; file references one level deep, relative paths from skill root.
- Validation: `skills-ref validate ./my-skill` from the reference library (https://github.com/agentskills/agentskills/tree/main/skills-ref). Its README (https://raw.githubusercontent.com/agentskills/agentskills/main/skills-ref/README.md): "intended for demonstration purposes only. It is not meant to be used in production"; commands `validate`, `read-properties`, `to-prompt` (emits XML for agent prompts). Python package, no PyPI install verified (UNVERIFIED). Whether it rejects non-spec keys like `disable-model-invocation` is UNVERIFIED (source not read).

### 4.2 Creator guides (T1, same site)
Pages (accessed 2026-10-01): https://agentskills.io/skill-creation/best-practices.md, `.../optimizing-descriptions.md`, `.../evaluating-skills.md`, `.../using-scripts.md` (not fetched).
- Best practices: start from real expertise (extract from a hands-on task; synthesize from runbooks, incident reports, review comments, version-control history), not from generic LLM knowledge; read execution traces; "Add what the agent lacks, omit what it knows"; coherent units (not too narrow, not too broad); moderate detail; defaults not menus; procedures over declarations; **Gotchas sections** ("the highest-value content in many skills"; keep them in SKILL.md and add every correction you had to make); output templates; checklists; validation loops; plan-validate-execute; bundle a script when every run reinvents the same helper; tell the agent *when* to load each reference file ("Read references/api-errors.md if the API returns a non-200").
- Description optimisation: imperative phrasing ("Use this skill when..."), user intent not implementation, "err on the side of being pushy", <= 1024 chars. Trigger evals: about **20 queries, 8-10 should-trigger and 8-10 should-not-trigger**, the negatives being near-misses; run each **3 times**, trigger rate threshold **0.5**; **60/40 train/validation split**; about 5 iterations; pick the best by validation pass rate. Includes a bash example detecting the Skill tool call with `claude -p "$query" --output-format json | jq ...` (needs `jq`; on Windows use Git Bash or a Node script).
- Output evals: `evals/evals.json` (`skill_name`, `evals[]` with `id`, `prompt`, `expected_output`, `files`, `assertions`), workspace `<skill>-workspace/iteration-N/eval-*/{with_skill,without_skill}/{outputs,timing.json,grading.json}` and `benchmark.json` with a `delta` of pass rate, time and tokens; start with 2-3 cases; drop assertions that always pass in both arms; require concrete evidence for PASS; keep subjective qualities for human review. Snapshot the old skill as the baseline when improving an existing one.
- Agreement across sources: Anthropic best practices, agentskills guides, OpenAI skill-creator and Matt's writing-for-agents all say: omit what the model already knows, progressive disclosure, specific defaults over menus, test with realistic prompts. Disagreement only on SKILL.md size (500 lines is a ceiling per spec/Anthropic; OpenAI says it is "not a target") and on manual-only for side-effect skills (see 3.3).

## 5. Cross-source convergence (what everyone agrees on)
1. A skill is a folder with `SKILL.md` + optional `references/`, `scripts/`, `assets/`, name equal to folder, description <= 1024 chars saying what AND when (T1: agentskills, Anthropic, OpenAI).
2. Keep SKILL.md short; disclose detail through one-level-deep references with an explicit "read X when Y" trigger (T1 all three; Matt).
3. Descriptions are the product: test triggering with should/should-not (near-miss) queries, 3 runs each (agentskills, Claude plugin eval, skill-creator).
4. Test outputs against a no-skill or old-skill baseline before believing a skill helps (agentskills, Anthropic best practices, skill-creator, `claude plugin eval` ablation).
5. Put correctness-critical or must-always-run rules in hooks or scripts, not prose (Claude memory docs, skills docs; agentskills "bundle scripts").
6. Manual-only for side-effect skills, expressed in BOTH harness formats (Claude frontmatter + Codex `agents/openai.yaml`) (Matt invocation.md; Claude docs; OpenAI openai_yaml.md).
