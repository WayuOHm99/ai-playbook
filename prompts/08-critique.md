# 08 - ให้ agent เห็นต่าง

หลักการ: agent มักตามใจคุณ ถ้าอยากได้คำค้านต้องสั่งให้ชัด ขอ verdict พร้อมหลักฐาน ไม่ใช่ "แผนนี้โอเคไหม" (skill: `grill-me`, `grill-with-docs`, `wayfinder`)
ทุก prompt ในไฟล์นี้ห้ามแก้ไฟล์ และควรรันก่อนอนุมัติสเปกหรือก่อนตัดสินใจเรื่องที่ย้อนกลับยาก

---

## 08-A คัดค้านแผนของฉัน (push back)

**ใช้เมื่อ:** มีแผนหรือการออกแบบ และอยากรู้ว่าจุดไหนอ่อน
**ได้อะไร:** สรุปที่เข้าใจ ทางเลือกที่แข็งที่สุดที่ไม่ได้เลือก คำตัดสิน (ไปต่อ / ไปต่อพร้อมแก้ / หยุด)

```text
ทำตัวเป็น senior reviewer ที่ไม่เกรงใจ ไม่ต้องเห็นด้วยกับฉัน ห้ามแก้ไฟล์
แผน/การออกแบบของฉัน: <วางหรือ @ไฟล์>
บริบท: ระบบ <ชื่อ> ระดับงาน <...> ข้อจำกัด <...> อ่าน CONTEXT.md/GLOSSARY.md และ ADR ที่เกี่ยวข้องด้วย

ตอบตามลำดับ
  1) สรุปแผนใน 2 ประโยคให้ฉันยืนยันว่าเข้าใจตรงกัน
  2) ทางเลือกที่แข็งที่สุดที่ฉันไม่ได้เลือก และทำไมอาจดีกว่า
  3) จุดที่อ่อนที่สุด 3 จุด พร้อมหลักฐานจากไฟล์หรือแหล่งที่ฉันให้ (อ้างไฟล์:บรรทัด)
  4) ถ้าสมมติฐานของฉันผิด ให้บอกตรงๆ ว่าผิดตรงไหน ไม่ต้องอ่อนลง
  5) คำตัดสิน: ไปต่อ / ไปต่อพร้อมแก้ / หยุด และการเปลี่ยนแปลงเดียวที่ลดความเสี่ยงได้มากที่สุด
ไม่ทำ: เห็นด้วยเพื่อให้ฉันสบายใจ แก้โค้ด หรือเสนอเขียนใหม่ทั้งหมดถ้าปัญหาแก้เฉพาะจุดได้
เสร็จเมื่อ: ฉันได้คำตัดสินพร้อมเหตุผลที่อ้างหลักฐานอย่างน้อย 3 ข้อ
รายงานเป็นภาษาไทย ไม่เกิน 1 หน้าจอ
```

## 08-B Pre-mortem (สมมติว่าล้มเหลวไปแล้ว)

**ใช้เมื่อ:** ก่อนอนุมัติสเปก ก่อนปล่อยระบบ หรือก่อนย้ายข้อมูลจริง
**ได้อะไร:** 5 สาเหตุที่เป็นไปได้มากที่สุดที่ระบบจะล้มเหลว พร้อมสัญญาณเตือนแรกและวิธีทดสอบถูกๆ

```text
ทำ pre-mortem สมมติว่า <โปรเจกต์ / การปล่อยครั้งนี้> ล้มเหลวหนักในโรงพยาบาลเมื่อ 6 เดือนจากนี้ (เช่น ข้อมูลผิด ไม่มีใครดูแลต่อ ถูกสั่งปิด ข้อมูลรั่ว) ห้ามแก้ไฟล์
ข้อมูลที่ใช้: <spec / แผน / @ไฟล์>; ผู้ใช้ <บทบาท>; ผู้ดูแลหลังส่งมอบ <ใคร หรือยังไม่มี>

ทำ
  1) สาเหตุที่เป็นไปได้ที่สุด 5 ข้อ เรียงตามโอกาส x ผลกระทบ แต่ละข้อมีสัญญาณเตือนแรกที่เห็นได้
  2) สมมติฐานที่ฉันพึ่งอยู่และอาจเป็นเท็จ พร้อมวิธีทดสอบถูกๆ ภายใน 1 วัน
  3) อย่างน้อย 1 ข้อที่เกี่ยวกับคนและกระบวนการ (ไม่มีคนดูแล ผู้ใช้ไม่ยอมเปลี่ยนจาก Excel ผู้ช่วยในทีมไม่ทำงานจริง) ไม่ใช่เรื่องโค้ดอย่างเดียว
  4) อะไรที่ทำวันนี้แล้วลดความเสี่ยงได้มากที่สุดภายใน 1 สัปดาห์
ข้อที่ไม่มีหลักฐานจากไฟล์ที่ให้ ให้ติดป้าย "ข้อสันนิษฐาน" และห้ามเขียนเหมือนข้อเท็จจริง
เห็นต่างได้: ถ้าเห็นว่าความเสี่ยงที่ฉันกลัวไม่ใช่ตัวจริง ให้บอก
เสร็จเมื่อ: มีตารางอันดับ 5 ข้อ + แผนลดความเสี่ยงที่ฉันเลือกทำได้ข้อแรกทันที
รายงานเป็นภาษาไทย
```

## 08-C "ฉันมองข้ามอะไรไปหรือเปล่า"

**ใช้เมื่อ:** รู้สึกว่าทุกอย่างดูโอเค แต่ไม่มั่นใจ หรือก่อนกดอนุมัติ "ตามคำแนะนำ" ติดกันหลายข้อ
**ได้อะไร:** รายการสิ่งที่ตกหล่นเรียงตามผลกระทบ พร้อมคำถามที่ฉันควรตอบให้ได้ก่อนไปต่อ

```text
ฉันกำลังจะ <ทำอะไร เช่น อนุมัติสเปก / ปล่อยระบบ / ตอบรับข้อเสนอของ agent> ช่วยบอกว่าฉันมองข้ามอะไรไป ห้ามแก้ไฟล์
บริบท: อ่าน <spec / STATE.md / CONTEXT.md/GLOSSARY.md / ผลรีวิวล่าสุด / BACKLOG.md>

ตรวจหาสิ่งที่ตกหล่นในด้านเหล่านี้ และบอกเฉพาะที่พบจริง
  - ข้อมูลผู้ป่วย/PDPA และใครมองเห็นอะไร
  - ตัวเลขเงินหรือกฎธุรกิจที่ฉันตอบรับไปโดยอธิบายให้ตัวเองฟังไม่ได้
  - ความต้องการที่ขัดกันระหว่างที่ตกลงไว้ช่วงต่างๆ
  - สิ่งที่ตรวจไม่ได้หรือยังไม่เคยทดสอบ
  - คนดูแลหลังส่งมอบ การสำรอง การกู้คืน
  - ขอบเขตที่ขยายเงียบๆ จากสิ่งที่ตกลงตอนต้น
ผลลัพธ์: ตารางสิ่งที่ตกหล่น | ทำไมสำคัญ | หลักฐาน | ตอบได้ด้วยคำถามข้อไหน | ผลกระทบ (สูง/กลาง/ต่ำ)
ถ้ามีเรื่องที่ฉันเคยตอบว่า "ตามคำแนะนำ" แต่ผลกระทบสูง ให้ดึงขึ้นมาอธิบายใหม่ใน 5 บรรทัดพร้อมตัวอย่างตัวเลข แล้วให้ฉันตอบ "เข้าใจแล้ว" หรือถามต่อ
ถ้าไม่พบอะไรในด้านไหน ให้บอกว่าตรวจอะไรไปแล้ว ห้ามเขียนว่าไม่มีโดยไม่ระบุ
ไม่ทำ: สร้างปัญหาเกินจริงเพื่อให้ดูละเอียด รายงานเฉพาะที่กระทบความถูกต้อง ความปลอดภัย หรือข้อกำหนด
เสร็จเมื่อ: ฉันได้รายการไม่เกิน 7 ข้อพร้อมคำถามที่ตอบได้
รายงานเป็นภาษาไทย
```

## 08-D ตรวจการตัดสินใจเทียบกับ ADR ที่มีอยู่

**ใช้เมื่อ:** จะเปลี่ยนสิ่งที่เคยตัดสินใจไว้ เช่น เปลี่ยนฐานข้อมูล ลบหน้า เปลี่ยนวิธีเก็บเงิน/วันที่
**ได้อะไร:** รายงานความขัดแย้งกับ ADR/glossary/.out-of-scope ก่อนลงมือ พร้อมร่าง ADR ใหม่หากจะเปลี่ยนจริง (skill: `domain-modeling`)

```text
ตรวจการตัดสินใจนี้เทียบกับของเดิมก่อน ยังไม่แก้โค้ด ยังไม่เขียน ADR จริงจนกว่าฉันตอบตกลง
การตัดสินใจที่จะทำ: <เช่น เปลี่ยนจาก MySQL เป็น PostgreSQL / ลบหน้าเปรียบเทียบ / เก็บจำนวนเงินเป็น decimal>
เหตุผลที่อยากทำ: <ปัญหาจริงที่เจอ>

ทำ
  1) อ่าน docs/adr/*, CONTEXT.md/GLOSSARY.md, decisions.md, .out-of-scope/ แล้วหา ADR หรือข้อตกลงที่เกี่ยวข้อง อ้างชื่อไฟล์และบรรทัด
  2) รายงานว่าการตัดสินใจใหม่ขัดกับข้อไหน ข้อไหนถูกแทนที่ ข้อไหนยังใช้ได้ และ ADR เดิมเขียนเหตุผลอะไรไว้ (เหตุผลนั้นยังจริงอยู่หรือไม่)
  3) ต้นทุนการย้อนกลับ (reversal cost) และสิ่งที่จะเสียไปจากงานที่ทำแล้ว
  4) ทางเลือกที่เล็กกว่าที่แก้ปัญหาเดิมได้โดยไม่ต้องเปลี่ยนการตัดสินใจ
  5) ถ้าควรเปลี่ยนจริง ร่าง ADR ใหม่: บริบท / ตัวเลือก / การตัดสินใจ / ผลที่ตามมา / เงื่อนไขที่ควรย้อนกลับ และระบุ ADR เดิมที่ถูกแทนที่
ไม่ทำ: ทำตามการตัดสินใจก่อนฉันตอบตกลง แก้ ADR เดิม (ADR เดิมห้ามแก้ ให้สร้างใหม่และทำเครื่องหมายว่าแทนที่)
เห็นต่างได้: ถ้าเห็นว่าเหตุผลของฉันไม่เพียงพอ หรือปัญหาจริงอยู่ที่อื่น ฟันธงตรงๆ
เสร็จเมื่อ: ฉันได้ verdict (เปลี่ยน / ไม่เปลี่ยน / เปลี่ยนเล็กกว่า) พร้อมรายการความขัดแย้งที่อ้างไฟล์ และร่าง ADR ถ้าเป็นกรณีเปลี่ยน
รายงานเป็นภาษาไทย ไม่เกิน 1 หน้าจอ ปิดท้ายด้วยคำถามข้อเดียวที่ฉันต้องตอบ
```
