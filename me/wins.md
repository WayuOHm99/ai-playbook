# Wins: สิ่งที่ได้ผลและควรทำซ้ำ

> หลักฐานเป็นโปรเจกต์ + วันที่ (เดือน-วัน) ไม่มีข้อมูลส่วนบุคคล/ความลับ/ตัวระบุโรงพยาบาล

## 1. เริ่มด้วยการคุยก่อน (question-first)
- ให้ agent สรุปความเข้าใจ ชี้ข้อติดขัดที่มองข้าม เสนอ stack แล้วถามไม่กี่ข้อ ก่อนแตะโค้ด
- หลักฐาน: EQ-PROJECT 08-01 (พบข้อติดขัดจริง 4 ข้อก่อนเริ่ม: คีย์รั่วจากเบราว์เซอร์, อ่าน PDF ภาษาไทย, ขีดจำกัดตัวอักษร, การใช้ข้อมูลของแพ็กเกจฟรี); claude-desktop 09-28; ชมรม (ถามก่อนเสมอ)
- ทำซ้ำ: ทุกโปรเจกต์ใหม่ ใช้ `prompts/01-start-project.md` (01-A)

## 2. แผน -> อนุมัติ -> ทำในขอบเขต -> รีวิวอย่างเดียว -> แก้เฉพาะ finding
- ขอ "เสนอแก้เล็กที่สุด ยังไม่แก้" แล้วข้อห้ามเป็นข้อๆ แล้วรีวิวแบบอ่านอย่างเดียวพร้อมรูปแบบ verdict
- หลักฐาน: SUTH helpdesk 08-10 (issue ปีงบประมาณ, AGENTS.md, การจัดโครงสร้างรีโป merge สะอาด CI เขียว); Run-Performance (18 task ผ่าน fast-forward โดยไม่มี commit หาย)
- ทำซ้ำ: เป็นแกนของ `prompts/05-review-audit.md` (05-B), `/ship` (แก้ไม่เกิน 2 รอบ)

## 3. ผู้รีวิวอิสระแบบ read-only ที่ไม่เชื่อรายงาน
- agent ตัวที่สองตรวจกับ repo จริง ("รายงานไม่ใช่ความจริง") และคุณไม่อนุมัติ merge จากรายงานอย่างเดียว
- หลักฐาน: RubricLens 08-08/08-17 (เจอ audit ที่ล้มจากสายพึ่งพา แก้แล้ว 0 vulnerabilities); SUTH 09-07 (ADR ที่อ้างกฎที่ไม่ได้ย้ายจริง, guard ที่ถูกข้าม, เทสต์ที่ขาด); Run-Performance (เทสต์ที่ผ่านลอยๆ, race condition, ล็อกที่อาจลบของที่ยังใช้)
- ทำซ้ำ: sub-agent `reviewer` (จำกัด 2 รอบตาม `me/pitfalls.md` ข้อ 3)

## 4. ประตูความปลอดภัยของข้อมูลจริง
- กัน PR ที่อาจมีข้อมูลจริง แล้วให้เป็น Draft จนสะอาด เขียนลง DB ได้เฉพาะฐานทดสอบที่ตั้งชื่อและตรวจ marker
- หลักฐาน: SUTH helpdesk 08-10 (สเปรดชีตตัวอย่าง untrack + git-ignore), 09-10 (QA เขียนเฉพาะ DB ทดสอบที่อนุมัติ); Run-Performance (canary พิสูจน์ว่า deny rules ทำงานใน worktree); บทเรียนจากเทสต์ที่เคยเขียนทับไฟล์สถานะจริง แก้แล้วมี regression test
- ทำซ้ำ: เป็นค่าเริ่มต้นของทุกโปรเจกต์ที่มีข้อมูลจริง

## 5. ยืนยันด้วยข้อมูลจริงและหาสาเหตุราก
- เทียบใบแจ้งหนี้จริงหลายงวดให้ตรงถึงหน่วยสตางค์ และอธิบายส่วนต่าง ±0.01 ด้วยกฎปัดเศษ; เก็บเงินเป็นจำนวนเต็มหลังตรวจพบ float คลาดเคลื่อน
- หาสาเหตุราก: หน้ารายการไม่รีเฟรชมาจาก CORS header ที่ขาด (มีหลักฐานก่อน/หลังและ regression test); CI ล้มใน 2 วินาทีมาจากบัญชีถูกล็อก ไม่ใช่โค้ด; แยก "ต้นทางไม่ส่งข้อมูล" ออกจาก "pipeline ของเราทำหาย"
- หลักฐาน: SUTH helpdesk 09-04, 09-10, 09-21, 09-23; Run-Performance (รายงาน health แบบ read-only)
- ทำซ้ำ: `prompts/03-bugs.md` (ทำซ้ำได้ก่อน -> สาเหตุราก -> เทสต์แดง -> แก้เล็กสุด) และแปะ error จริงพร้อม request id

## 6. พรอมต์แก้บั๊กเดียวที่มีรั้วแน่น
- หลักฐานข้อเท็จจริง 2-4 ข้อ, ขอบเขตเป็นข้อ, ห้ามสำรวจทั้ง repo, เทสต์เฉพาะจุดแล้วเต็มชุด, ยังไม่ commit, edge case อื่นให้จดไว้
- หลักฐาน: Run-Performance 08-17 (บั๊กตัวกรอง lap สั้น ชุดทดสอบเต็ม 104 ผ่าน และคุณเลือกพัก edge case เองอย่างมีสติ)
- ทำซ้ำ: ใช้ `prompts/03-bugs.md` (03-C)

## 7. เพิ่มการเฝ้าระวังทีละเครื่องมือ
- แต่ละขั้น: อ่านโค้ดจริง -> เสนอแผน -> รออนุมัติ -> ทดสอบบนเครื่องจริง -> ค่อย commit
- หลักฐาน: Run-Performance 08-05 ถึง 08-17 (lock -> CI -> health report -> pilot บน lane เดียว -> Sentry) เป็นกระบวนการที่เรียบร้อยที่สุดในประวัติทั้งหมด
- ทำซ้ำ: กับทุกการเพิ่มโครงสร้างพื้นฐาน

## 8. มาโครปิดงาน end-to-end
- "ปิดงาน #N end-to-end" พร้อมรายการที่อนุญาตและห้าม แทนพรอมต์ ~6 ข้อความต่อ issue
- หลักฐาน: SUTH helpdesk 09-23 (agent อธิบายว่าต้องสั่งชัดเจน แล้วมาโครได้ผลทันที)
- ทำซ้ำ: `/ship` แทน "อนุมัติหมด"

## 9. สัมภาษณ์ `grill-with-docs` + บันทึกเป็นลายลักษณ์อักษร
- 14-26 คำถาม แต่ละข้อมีคำตอบที่แนะนำ ตัดสินได้เร็ว ได้ ADR และแผนเป็นเฟส
- หลักฐาน: SUTH helpdesk 09-12 (ADR-0021..23); CAMPBANK 08-21 (spec + grill + roadmap)
- ทำซ้ำ: แต่จำกัดราว 10 คำถามต่อรอบ มีคำตอบตั้งต้นและกติกาหยุด เพราะคุณเหนื่อยกับจำนวนคำถามมาก

## 10. ส่งต่อด้วยไฟล์ ไม่ใช่ด้วยความจำ
- HANDOFF / PROJECT-STATE / next-session-scope และ handoff ที่ระบุ "ทำแล้ว / ทดสอบแล้ว / ยังไม่ทำ / ห้ามอนุมัติเอง" ทำให้ผู้รับเริ่มต่อได้ทันที
- หลักฐาน: SUTH helpdesk 09-15, 09-21 (ADR-0018/0019 ห้ามอนุมัติสถานะติดตั้งและราคาในอดีต); RubricLens 08-08/08-17; ชมรม 07-12/13; D_ 09-19 ถึง 09-21
- ทำซ้ำ: `/handoff-pack` (ทั้งฝั่งเขียนและฝั่งรับงาน)

## 11. การแบ่งบทบาทที่เขียนเป็นสัญญา
- แหล่งความจริงเรียงลำดับ, ผู้เขียนหนึ่งคนต่อ task, worktree ต่อ task, ผู้รีวิวไม่แก้, คุณเป็น Product Owner ที่พูดแค่อนุมัติ/ปฏิเสธ
- หลักฐาน: Run-Performance platform (18 task ไม่มี commit หาย); RubricLens (Claude สองตัวอ่านอย่างเดียว + Codex ตรวจ)
- ทำซ้ำ: กับงานความเสี่ยงสูง แต่ใช้ตัวเดียวเป็นค่าเริ่มต้นสำหรับโปรเจกต์เล็ก

## 12. ตัดงานเองหลังเจอปัญหาจริง
- ลบเอกสารบวม, MCP server, Actions/nightly, หน้า ranking/compare ที่ไม่คุ้ม; ตัด issue ที่กว้างเกินไปเอง
- หลักฐาน: SUTH helpdesk 09-03/04, 09-10, 09-16 (ตัด #51), 09-19 ถึง 09-21; Run-Performance 08-03, 08-17, 09-29 (ตัดเหลือ Garmin-only)
- ทำซ้ำ: เก็บนิสัยนี้ แต่ย้ายมาก่อนสร้าง (ถามว่า "ตัวเลขนี้ช่วยตัดสินใจอะไร") และจดเงื่อนไขกู้คืนก่อนลบ

## 13. งานที่มีชิ้นงานจับต้องได้และเดดไลน์จริง
- ส่งมอบสำเร็จสม่ำเสมอ: trainer-app (เฟสเล็กที่ยืนยันทีละเฟส ผู้ใช้จริง), treadmill-sprint (งานอีเวนต์), RubricLens, CAMPBANK (ใช้งานจริงแล้ว), วิดีโอชมรมแต่ละคลิป
- ทำซ้ำ: ตั้ง "ชิ้นงานที่กดได้/ดูได้ + วันส่ง" ตั้งแต่ต้น และแบ่งเฟสเล็ก

## 14. ห้องฝึก (practice lab) และ canary
- บั๊กที่วางไว้ เทสต์ก่อน พิสูจน์ว่าเทสต์ล้มได้จริง พรอมต์ดักใจ ("แก้เทสต์ด้วย รีบอยู่") ที่ agent หยุดถามและคุณตอบด้วยเงื่อนไข; รหัส canary พิสูจน์ว่า AGENTS.md ถูกอ่าน
- หลักฐาน: C_Users 08-17
- ทำซ้ำ: ใช้ canary ตอนเริ่มทุกโปรเจกต์ (sub-agent `verifier`) และกฎ "ห้ามผ่อนเทสต์"

## 15. ให้ agent เห็นต่างและชี้สิ่งที่มองข้าม; ข้อเท็จจริงในเอกสาร
- คำสั่ง "ถามฉันถ้ามองข้ามอะไร" นำไปสู่การค้นพบที่แก้ได้ (เช่นประวัติแชทถูกลบทุก 30 วัน, ตั้งเป็น 365 วัน)
- กติกา "ใช้เฉพาะสิ่งที่ระบบพิสูจน์ได้ ห้ามเดา ถามฉัน" สำหรับรายงาน/ข้อเสนอทุน (SUTH helpdesk 09-23) ปกป้องความน่าเชื่อถือของคุณ
- ทำซ้ำ: ใส่เป็นบรรทัดมาตรฐานใน AGENTS.md และ รูปแบบรายงานใน `instructions/core.md`
