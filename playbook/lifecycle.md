# วงจรงานตั้งแต่ 0 ถึงส่งมอบ

> สรุปจาก `research/01-agent-workflows.md` ซึ่งอ้างอิง Anthropic, OpenAI, Matt Pocock, Addy Osmani, Kent Beck และแหล่งอื่น ตรวจเมื่อ 2026-10-01
> ทุกขั้นมี **ประตู (gate)** ไม่ผ่านประตูของขั้นนี้ ห้ามไปขั้นถัดไป

## ภาพรวม

```
0 ตั้งค่า → 1 คัดแยก → 2 ซักถาม → 3 ค้นข้อมูล → 4 spec → 5 ตัดสินใจเทคนิค → 6 เตรียมโปรเจกต์
   → 7 แตก ticket → [8 เขียนโค้ด → 9 ตรวจในแอปจริง → 10 review]  ← วนทีละ ticket ด้วย /ship
   → 11 deploy → 12 ส่งมอบ → 13 ดูแลต่อ
```

คุณต้องตัดสินใจแค่ 3 จุด: **อนุมัติ spec (ขั้น 4)**, **merge / deploy (ขั้น 10–11)** และ **ตอบคำถามตอนซักถาม (ขั้น 2)**

## ระดับงาน: เลือกก่อนเริ่ม เพื่อไม่ให้สร้างเกินจำเป็น

| ระดับ | ใช้เมื่อ | ต้องมี |
|---|---|---|
| **demo** | ทดลอง พรีเซนต์ งานส่วนตัว | รันได้, README สั้นๆ |
| **ใช้ภายใน** | คนในโรงพยาบาลใช้จริงแต่ไม่ใช่ระบบวิกฤต | + test หลัก, login, backup, `HANDOVER.md` |
| **ใช้จริง** | ข้อมูลบุคคล / ข้อมูลผู้ป่วย / งานที่หยุดไม่ได้ | + audit log, PDPA checklist, restore drill, monitoring, security review |

รายละเอียดแต่ละระดับอยู่ใน `stacks/hospital-web.md`

## ทีละขั้น

| # | ขั้น | เป้าหมาย | ประตู (ผ่านเมื่อ) | สกิล / ตัวช่วย |
|---|---|---|---|---|
| 0 | **ตั้งค่าโปรเจกต์** (ครั้งเดียว) | ไม่ต้องตอบคำถาม setup ซ้ำ | มี `AGENTS.md`, `CLAUDE.md`, `STATE.md`, `BACKLOG.md`, `DECISIONS.md` และคำสั่ง verify คำสั่งเดียว | `templates/project/`, `/setup-matt-pocock-skills` + `setup/matt-pocock-setup-answers.md` |
| 1 | **คัดแยก** | รู้ว่างานนี้เป็นประเภทไหน ก่อนแตะโค้ด | จัดเป็น P0–P7 และรู้ว่าไปขั้นไหน | `/new-request`, `/triage` |
| 2 | **ซักถาม** | ดึงสิ่งที่ยังไม่รู้ออกมาครั้งเดียว | ไม่เหลือคำถามค้าง, มีรายการความเสี่ยง, ตอบเรื่องข้อมูลส่วนบุคคลและเครือข่ายโรงพยาบาลแล้ว | `/grill-with-docs` (ใน repo), `/grill-me` (นอก repo), `/wayfinder` (งานใหญ่หลายวัน) |
| 3 | **ค้นข้อมูล** | ตัดสินใจจากข้อมูลจริงล่าสุด | ทุกคำถามมีแหล่งอ้างอิงพร้อมวันที่ หรือติดป้าย UNVERIFIED | `/research`, sub-agent `researcher` |
| 4 | **Spec** | เขียนให้ชัดครั้งเดียวว่าทำอะไร และ **ไม่ทำอะไร** | มีหัวข้อ Out of Scope, วิธีตรวจว่าเสร็จ, คุณอนุมัติแล้ว | `/to-spec` |
| 5 | **ตัดสินใจเทคนิค** | จดการตัดสินใจที่ย้อนกลับยาก | 1 ADR ต่อ 1 การตัดสินใจ มีทางเลือกอื่นที่เคยพิจารณา | `/domain-modeling`, `engineering:architecture` |
| 6 | **เตรียมโปรเจกต์** | ตรวจงานได้ก่อนมีฟีเจอร์ | test, typecheck, lint, build ผ่านด้วยคำสั่งเดียว | agent หลัก |
| 7 | **แตก ticket** | หั่นงานเป็นชิ้นที่ตรวจได้ทีละชิ้น | แต่ละ ticket จบได้ใน 1 เซสชัน มีเกณฑ์รับงาน | `/to-tickets` |
| 8 | **เขียนโค้ด** | ทำทีละ ticket เขียน test ก่อน | test, typecheck, lint เขียว, diff อยู่ในขอบเขต ticket | `/ship` (ใช้ `/implement` + `/tdd` ข้างใน) |
| 9 | **ตรวจในแอปจริง** | พิสูจน์ว่าใช้ได้จริง ไม่ใช่แค่ test ผ่าน | เปิดแอป ทำตามขั้นตอนของ ticket มีภาพหรือผลเป็นหลักฐาน | sub-agent `verifier` |
| 10 | **Review** | ตรวจด้วยสายตาใหม่ | รายงานแยก Spec กับ Standards, แก้ BLOCKER แล้ว, แก้ไม่เกิน 2 รอบ | `/code-review`, sub-agent `reviewer` |
| 11 | **Deploy** | ปล่อยแบบถอยกลับได้ | backup แล้ว, ทดสอบ migration กับสำเนา, มีแผนถอยกลับ, **คุณเป็นคนกด** | `engineering:deploy-checklist` |
| 12 | **ส่งมอบ** | คนอื่นดูแลต่อได้ | agent ตัวใหม่ทำตาม `HANDOVER.md` ได้โดยไม่ติด | prompt handover |
| 13 | **ดูแลต่อ** | เก็บ backlog กับเอกสารให้สะอาด | คัดแยก BACKLOG สัปดาห์ละครั้ง, อัปเดต dependency | `/triage` |

Guard hooks เป็นตัวเลือกที่ต้องเปิดใช้เอง ปัจจุบัน playbook guard ไม่ได้ติดตั้ง และ `sync.ps1` ไม่ติดตั้งให้ จึงไม่เป็น gate ของขั้น 6 กติกาใน `instructions/core.md` เป็นคำสั่งให้ agent ทำตาม ไม่ใช่กลไกบล็อกคำสั่ง ดู [สถานะ guard](../guardrails/README.md) ก่อนพึ่งการป้องกันนี้ หากโปรเจกต์กำหนด hook ของตัวเอง ให้ตรวจตามกฎของโปรเจกต์นั้น

## งานเล็กไม่ต้องทำครบทุกขั้น
- **แก้บั๊ก:** 1 → เขียน test ให้เกิดซ้ำ → 8 → 9 → 10
- **แก้ข้อความหรือสีเล็กน้อย:** 1 → 8 → 9 (ถ้าอธิบาย diff ได้ในประโยคเดียว ไม่ต้องทำ spec)
- **ฟีเจอร์ใหม่:** ทำครบ 1 → 10

## หลักที่ใช้ทุกขั้น
- **1 ticket ต่อ 1 เซสชัน** เปลี่ยนงานเมื่อไหร่ให้ `/clear` หรือเปิดเซสชันใหม่
- **แก้ 2 ครั้งแล้วยังผิด** ให้ `/clear` แล้วเขียน prompt ใหม่จากสิ่งที่เรียนรู้ อย่าแก้วนต่อ
- **หลักฐาน ไม่ใช่คำพูด** ทุก "เสร็จแล้ว" ต้องมีชื่อ test, คำสั่งที่รัน หรือภาพหน้าจอ
- **หลังจบแต่ละ ticket** ถาม agent ว่า "อธิบาย design นี้ให้ฟัง และจุดที่อาจพังคืออะไร" เพื่อให้คุณเข้าใจระบบของตัวเอง งานวิจัยของ Anthropic พบว่าคนที่ถามเชิงแนวคิดเข้าใจโค้ดดีกว่าคนที่สั่งให้เขียนอย่างเดียวอย่างชัดเจน
